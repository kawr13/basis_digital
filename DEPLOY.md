# Выкат на сервер без .env

Кабинет поднимается **одной командой** — `./deploy.sh`. Скрипт сам генерирует
секреты, сам всё подставляет и сам запускает контейнеры. **Файл `.env` в
репозитории не появляется никогда** (`.env` в `.gitignore`, в git попадает
только `.env.example` как справочник). Ниже есть и ручная дорожка через
`export` — если хочется контролировать каждую переменную.

## 1. Пакеты и доступы

- Docker Engine + compose plugin (`docker compose version`).
- Наружу по умолчанию не открыто ничего: `WEB_PORT` (8080) публикуется только
  на `127.0.0.1` (`WEB_BIND=127.0.0.1`) — извне кабинет виден лишь через
  хостовый nginx/Caddy либо после `WEB_BIND=0.0.0.0`. PostgreSQL и бэкенд
  наружу не смотрят — у сервиса `db` портов нет вовсе.

## 2. Выкат одной командой

```bash
git clone https://github.com/kawr13/basis_digital.git
cd basis_digital
./deploy.sh
```

Готово: скрипт выведет адрес и логин `admin`, а пароль покажет **один раз** — при
первом запуске. Дальше его читать так:

```bash
sed -n 's/^ADMIN_PASSWORD=//p' /etc/basis_digital/deploy.env
```

Что делает `deploy.sh`:
- проверяет docker и compose;
- ищет файл секретов в порядке `$BASIS_DIGITAL_HOME` → `/etc/basis_digital/deploy.env`
  → `~/.config/basis_digital/deploy.env` (первый найденный и есть настоящий); если
  файла нет — создаёт: root пишет в `/etc/basis_digital`, обычный пользователь — в
  `~/.config/basis_digital`. Путь больше не зависит только от `$HOME`: раньше запуск
  одного и того же сервера то из-под root, то из-под своей учётки создавал **второй**
  файл с новым `POSTGRES_PASSWORD`, том `pgdata` оставался со старым паролем, и
  кабинет умирал на старте (в браузере — 502 и «пропали пользователи»);
- генерирует `POSTGRES_PASSWORD`, `SECRET_KEY`, `ADMIN_PASSWORD` **один раз** и больше
  их не меняет: пароль БД PostgreSQL применяет только к пустому тому;
- **до сборки** проверяет, что `POSTGRES_PASSWORD` из секретов действительно подходит к
  уже инициализированному тому `pgdata` — по IP контейнера базы, то есть из той же
  подсети и по тому же `scram`, что и приложение. К `127.0.0.1` внутри контейнера
  `pg_hba.conf` часто пускает по `trust`, и проверка на этом пути врёт. Рядом
  прогоняется заведомо неверный пароль: пустит и с ним — значит путь `trust`, и
  скрипт скажет, что проверить не может, вместо ложного «ок». Статус `db (healthy)`
  тоже ничего не доказывает: `pg_isready` засчитывает ответ сервера даже при отказе
  аутентификации;
- **расхождение пароля чинит сам**: `ALTER USER` через unix-сокет, а если `local` тоже
  под паролем — временно включает `trust` в `pg_hba.conf`, меняет пароль и возвращает
  конфиг обратно. Том с данными не трогается; `--no-auto-fix` отключает починку;
- после сборки сверяет **внутри работающего контейнера** `backend` окружение с
  секретом: `DATABASE_URL` (compose собирает в неё пароль БД — отдельной
  переменной `POSTGRES_PASSWORD` в контейнере нет) и `SECRET_KEY`, при
  расхождении пересоздаёт контейнер: compose считает контейнер актуальным, пока
  не изменилось описание сервиса, а переменная из `--env-file` в нём могла
  остаться от прошлой жизни;
- предупреждает, если рядом найден том `pgdata` от старых выкатов: имя
  compose-проекта зафиксировано (`name: statcab`, том `statcab_pgdata`), но тома
  времён до фиксации назывались по имени папки — данные могут лежать в них (§7);
- запоминает `WEB_PORT`, HTTPS-режим и overlay-файлы в том же файле секретов: повторный
  `./deploy.sh` без флагов повторяет прошлый запуск, а не возвращает порт 8080 и не
  снимает overlay с TLS (иначе кабинет за хостовым nginx снова публиковал `0.0.0.0:8080`);
- после запуска ждёт зелёного `/healthz` через nginx — то есть проверяется вся цепочка
  `web → backend → PostgreSQL`, — а не просто «контейнеры в Up»; при неудаче печатает
  лог бэкенда и статус;
- `CORS_ORIGINS` не трогает: фронт и API на одном адресе (nginx проксирует
  `/api/`), запросы однопоточные по origin — CORS в проде не участвует.

Ключи: `--http` / `--https`, `--port 9000`, `--with deploy/nginx/docker-compose.host-nginx.yml`
(overlay, запоминается), `--fix-db-password` (согласовать пароль в базе с секретом,
обычно не нужен — `./deploy.sh` делает это сам), `--no-auto-fix` (найти расхождение,
но не менять), `--show-password`, `--check` (только проверки, ничего не пересобирать),
`--help`.

## 3. Ручная дорожка (если без скрипта)

Только две переменные по-настоящему обязательны — без них compose не стартует.

```bash
export POSTGRES_PASSWORD="$(openssl rand -hex 16)"   # пароль БД
export SECRET_KEY="$(openssl rand -hex 32)"          # подпись JWT
export ADMIN_PASSWORD="$(openssl rand -hex 8)"       # пароль админа при первом старте
export COOKIE_SECURE=false                           # HTTP-сервер; при HTTPS — не задавать
docker compose up -d --build
```

| переменная | зачем | по умолчанию |
|---|---|---|
| `POSTGRES_PASSWORD` | пароль PostgreSQL, **обязательна** | — (compose не стартует) |
| `SECRET_KEY` | подпись токенов, **обязательна** | — (compose не стартует) |
| `ADMIN_PASSWORD` | пароль `admin` при первом запуске (иначе случайный — в лог) | пусто |
| `COOKIE_SECURE` | `false` для HTTP; пусто = «Secure при ENVIRONMENT=prod» | пусто |
| `WEB_PORT` | порт кабинета на сервере | `8080` |
| `UVICORN_WORKERS` | воркеры бэкенда (планировщик и синк живут в процессе, держим 1) | `1` |
| `ONE_C_SOURCE` | `mock` (витрина на заглушке) или `http` (боевая 1С, см. `docs/03`) | `mock` |

`CORS_ORIGINS` в проде не нужен (тот же origin). Нужен только если фронт
отдельно от бэкенда — тогда укажите адрес браузера.

## 4. Проверить запуск

```bash
docker compose ps                                   # все три сервиса Up; backend — healthy, когда витрина готова
docker compose logs backend | grep администратор     # пароль первого админа (ручная дорожка)
```

`backend (healthy)` — это проба готовности `/readyz` (он же `/api/readyz`): 200,
когда база жива и последняя успешная загрузка из 1С не старше настройки
`sync.age_limit_sec` (по умолчанию 5400 с); иначе 503 с `reason`. Токен пробы
заводится в одном месте — в админке (`service.readyz_token`) **или** в
`READY_TOKEN` (секреты/`.env`): `/readyz` принимает любое из двух значений.
Healthcheck контейнера токена не требует: 403 для него — «приложение живо».

Кабинет — на `http://localhost:8080` **с самого сервера**: по умолчанию
`WEB_BIND=127.0.0.1` и наружу порт не торчит. Варианты наружу: хостовый
nginx/Caddy (см. `docs/06`, §5) или осознанный `WEB_BIND=0.0.0.0` без TLS.
Вход: `admin` + `ADMIN_PASSWORD` (смените при первом входе).

## 5. Обновление

```bash
cd basis_digital
git pull
./deploy.sh            # секреты переиспользуются, пересоберутся только новые слои
```

Данные БД живут в томе `pgdata`, данные кабинета — в `statcab_data`;
`git pull` и пересборка их не трогают.

Прежде чем делать `git pull` на сервере — взгляни на CI
(`.github/workflows/ci.yml`, TASKS2.md п. 23): на каждый push/PR он гоняет
pytest бэкенда и сборку фронта. С красной сборки не выкатываем.

## 6. Бэкап и откат

```bash
# бэкап — скрипт deploy/backup.sh (TASKS2.md п. 22): пишет дамп во временный
# файл, проверяет его читаемость (pg_restore --list) и ротирует старые копии;
# битый дамп — ненулевой код возврата, cron заметит.
BACKUP_DIR=/var/backups/statcab POSTGRES_PASSWORD=*** ./deploy/backup.sh
# У compose-сервиса db порт наружу не торчит: на сервере скрипт запускают
# контейнером postgres:16 в сети statcab_default — рецепт и восстановление
# дампа — в docs/06_деплой_на_сервер.md, §6.

# откат кода:
git log --oneline -5
git checkout <коммит>
docker compose up -d --build
```

Откат по базе — не только `git checkout`: вкладка «База данных» в админке хранит
адрес сервера в самой базе (`.env` при этом не меняется). Кнопка «Вернуть ENV»
переключает кабинет обратно на `DATABASE_URL` из окружения, а если к прежней базе
уже не подключиться — она лишь снимает указатель, и на прежнюю базу процесс
вернётся после перезапуска («Перезапустить сервис» там же или
`docker compose restart backend`). Порядок отката целиком: база → код → том,
дамп и восстановление — §6 `docs/06_деплой_на_сервер.md`; там же §11 про смену
базы из браузера.

## 7. Не заводится

| симптом | куда смотреть |
|---|---|
| 502 на `/api/...`, при этом кабинет открылся | `docker compose logs backend` — почти всегда бэкенд упал на старте, nginx просто некому отвечать |
| `FATAL: password authentication failed for user "statcab"` | секреты разошлись с томом: файл секретов пересоздали (другой пользователь, другой сервер, удалённый файл), а `pgdata` остался со старым паролем. Обычный `./deploy.sh` замечает это до сборки и чинит сам: `ALTER USER` приводит пароль в базе к секрету, том с данными не трогается. Посмотреть без изменений — `./deploy.sh --check`; оставить пароль в базе как было — `./deploy.sh --no-auto-fix` (он подскажет, где искать старый `deploy.env`) |
| «Пропали» пользователи / база стала пустой | **данные никуда не делись, вы не оттуда смотрите.** Имя compose-проекта зафиксировано (`name: statcab`), рабочий том — `statcab_pgdata`, запуск из другой папки его же и использует. Пустая база означает том **до** фиксации имени: `docker volume ls` (там мог лежать `<имя_папки>_pgdata`), затем `docker volume inspect <том> --format '{{ index .Labels "com.docker.compose.project.working_dir" }}'` — и перенести данные в `statcab_pgdata` восстановлением из дампа |
| `db` показан `healthy`, но бэкенд не подключается | `pg_isready` проверяет только «сервер отвечает»; аутентификацию — `docker compose logs backend` |
| `POSTGRES_PASSWORD is missing a value` | вы не через `./deploy.sh` и не экспортировали переменные |
| 401 сразу после логина на HTTP | не хватает `COOKIE_SECURE=false` (это делает `./deploy.sh` без `--https`) |
| `db` не становится healthy | `docker compose logs db` |

⚠️ **`docker compose down -v` удаляет тома вместе с данными.** Останавливать —
`docker compose stop`. Если том всё же удалён, остаются только дампы из §6.

Подробности (ресурсы, HTTPS, nginx перед контейнером) — `docs/06_деплой_на_сервер.md`.
