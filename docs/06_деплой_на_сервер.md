# 06. Деплой на сервер (расчёт на ~10 одновременных пользователей)

Кабинет уже упакован в Docker Compose: `db` (PostgreSQL 16) + `backend`
(FastAPI/uvicorn) + `web` (nginx: SPA + прокси `/api`). Ручной сборки не нужно.

---

## 1. Хватит ли сервера на 10 человек — да, с запасом

| Ресурс | Минимум | Комфортно |
|---|---|---|
| CPU | 2 vCPU | 4 vCPU |
| RAM | 4 ГБ | 8 ГБ |
| Диск | 40 ГБ SSD | 80 ГБ (под бэкапы и .xlsm) |
| ОС | Ubuntu 22.04/24.04 LTS, Debian 12 | + Docker Engine + compose plugin |

Запас прочности: uvicorn работает в один воркер (`UVICORN_WORKERS=1` по
умолчанию: планировщик и блокировка синхронизации живут внутри процесса),
пул SQLAlchemy 10+20 соединений → максимум 30 подключений к Postgres при
штатных 100. Десять диспетчеров, открывающих дашборды раз в минуту, дадут
единицы RPS — узкое место наступит ориентировочно после 50+ активных
пользователей (см. §9).

## 2. Собрать и загрузить архив

С рабочей машины (Windows):

```powershell
cd D:\basis\statcab
powershell -ExecutionPolicy Bypass -File .\pack_release.ps1
# → release\statcab-<stamp>.zip (без node_modules, .git, .env, локальных БД)
```

Донести до сервера (scp/winscp/git push — что принято):

```bash
scp release\statcab-*.zip user@server:/tmp/
ssh user@server
sudo mkdir -p /opt/statcab && sudo tar -xf /tmp/statcab-*.zip -C /opt/statcab --strip-components=1
# или unzip; внутри должен лежать docker-compose.yml
```

Альтернатива архиву — git: `git clone` на сервер и `git pull` для обновлений.
Архив удобнее, когда сервер без доступа к репозиторию.

## 3. Настроить окружение

```bash
cd /opt/statcab
cp .env.example .env
openssl rand -hex 32   # → SECRET_KEY
openssl rand -hex 16   # → POSTGRES_PASSWORD
$EDITOR .env
```

Обязательно заполнить: `POSTGRES_PASSWORD`, `SECRET_KEY`, `ADMIN_PASSWORD`
(если оставить пустым — случайный пароль напечатает в лог при первом запуске).

**Главный развилочный флаг — `COOKIE_SECURE`:**

| Доступ к кабинету | COOKIE_SECURE |
|---|---|
| HTTPS (домен/сертификат) | оставить пустым (авто: Secure) |
| Внутренний сервер по `http://IP:порт` | `false` |

Если при `ENVIRONMENT=prod` и пустом флаге заходить по http — браузер не
примет refresh-cookie, и пользователей будет выкидывать каждые
`ACCESS_TOKEN_TTL_MINUTES` (30 мин). Это не ошибка входа, а именно флаг.

`CORS_ORIGINS` можно не трогать, если фронт и API идут через один nginx
(один origin). Отдельный домен для фронта — вписать его адрес.

## 4. Запуск

```bash
cd /opt/statcab
docker compose up -d --build        # первая сборка ~5 минут
docker compose logs backend | grep -i админ   # пароль админа, если не задан
curl -s http://localhost:8080/healthz         # → ok
```

Проба живости — `/healthz`, готовности — `/readyz` (он же `/api/readyz`, nginx
проксирует наружу оба; запросы пробы в access-лог не пишутся — токен из
query-строки не должен оседать в `docker logs`). `/readyz` отвечает 200, только
когда база жива и последняя успешная загрузка из 1С не старше настройки
`sync.age_limit_sec` (по умолчанию 5400 с); иначе 503 с полем `reason` — «жив,
но показывает устаревшее» не должно теряться ни в `docker compose ps`, ни у
внешнего мониторинга. Токен пробы заводят в ОДНОМ месте: в админке
(`service.readyz_token`) или в `READY_TOKEN` — `/readyz` принимает любое из двух
значений, а healthcheck контейнера токена не требует вовсе (403 для него —
«приложение живо»). Уточнение про `READY_TOKEN`: при выкате через `deploy.sh`
compose читает файл секретов (`--env-file`), а не `.env` рядом с compose; `.env`
актуален только для ручных `docker compose` без скрипта.

Открыть `http://localhost:8080` с самого сервера — по умолчанию кабинет
публикуется только на loopback (`WEB_BIND=127.0.0.1`); наружу его выводят
хостовый nginx/Caddy из §5 или осознанный `WEB_BIND=0.0.0.0` (HTTP без TLS).
Войти под `admin`, сменить пароль.
Таблицы создаются автоматически при старте (`init_db`), миграции колонок —
тоже (`_ADDED_COLUMNS` в `db.py`).

Файрвол: наружу не торчит ничего — `WEB_PORT` (8080) по умолчанию привязан к
`127.0.0.1` (`WEB_BIND`), Postgres и backend внутри compose-сети не
опубликованы — так и оставить.

О чём compose заботится сам и что не надо «допиливать»: `name: statcab` (том
`statcab_pgdata` не зависит от имени папки), `shm_size: 256mb` у базы (64 МиБ
из коробки — это `could not resize shared memory segment` на первом же
параллельном VACUUM или CREATE INDEX) и ротация json-логов (`max-size: 20m`,
`max-file: 5`): без неё json-file растёт, пока не забьёт `/var/lib/docker`, а
дальше PostgreSQL падает на «no space left on device».

## 5. Доменное имя, nginx и HTTPS

Общее для всех вариантов:

1. **DNS**: A-запись `cab.example.ru` → IP сервера (в интранете — внутренняя
   DNS-зона или `hosts` на машинах пользователей).
2. **Порты**: снаружи 80 и 443; порт кабинета 8080 наружу лучше не отдавать —
   прокси-оверрайды ниже сами прячут его на `127.0.0.1`.
3. **`.env`**: `CORS_ORIGINS=https://cab.example.ru`, `COOKIE_SECURE=` оставить
   пустым (авто: Secure — при HTTPS это то, что нужно).
4. **`X-Forwarded-For` обязателен**: тротлинг входа (`login_throttle_per_ip`)
   и AuditLog берут IP из этого заголовка. Не передаст внешний прокси —
   все 10 человек окажутся одним «127.0.0.1»: лимит 20 входов/мин делится
   на всех, аудит бесполезен. В примерах ниже заголовки уже проставлены.

Внутренний nginx кабинета сам раскладывает `/api` → backend, `/` → SPA —
внешний проксирует на него **всё одним upstream**, дублировать маршруты не надо.

### 5.1 На сервере уже стоит nginx (классика)

```bash
# 1) кабинет слушает только localhost
docker compose -f docker-compose.yml -f deploy/nginx/docker-compose.host-nginx.yml up -d

# 2) vhost (шаблон deploy/nginx/statcab.vhost.conf, поправить server_name)
sudo cp deploy/nginx/statcab.vhost.conf /etc/nginx/sites-available/statcab
sudo ln -s /etc/nginx/sites-available/statcab /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 3) сертификат Let's Encrypt (допишет ssl-блок сам)
sudo certbot --nginx -d cab.example.ru
```

### 5.2 nginx на хосте не нужен — Caddy внутри Docker (сертификаты сам)

```bash
# правка deploy/caddy/Caddyfile: свой домен вместо cab.example.ru
docker compose -f docker-compose.yml -f deploy/caddy/docker-compose.caddy.yml up -d
docker compose logs caddy        # выпуск сертификата с первого раза может занять минуту
```

Caddy выпускает и продлевает Let's Encrypt автоматически — нужен только
доступ из интернета на 80/443. Внутри compose он доходит до `web:80`,
наружу кабинет не торчит вообще.

### 5.3 Внутренний домен без доступа из интернета

Публичный сертификат Let's Encrypt получить нельзя (домен не виден снаружи).
Варианты, от лучшего к простому:

- **Свой корпоративный CA** — выпустить сертификат на `cab.internal`,
  корневой сертификат раздать на машины (GPO) — HTTPS как у людей.
- **Self-signed** + добавление сертификата в доверенные — работает, но
  противно администрировать.
- **Просто `http://cab.internal`** — тогда в `.env` `COOKIE_SECURE=false`
  (см. §3) и доступ по firewall только из подсети офиса.

### 5.4 gzip для API и размер тела запроса

nginx проксируемые ответы по умолчанию **не сжимает**: `gzip on` и
`gzip_types application/json` работают только на статику, а весь API — это
`proxy_pass` (годовое `overview` шло 743 КБ вместо ~60 КБ). Выключатель —
`gzip_proxied any;`, и он нужен в обоих конфигах: внутреннем и внешнем
(иногда vhost остаётся единственным nginx, §5.1). Там же `client_max_body_size
16m`: «Отчёт диспетчера» едет из браузера в base64 (+33 % к весу), при 2m
nginx отвечал 413 ещё до кода приложения.


## 6. Бэкапы (настроить в первый же день)

Бэкап — скрипт `deploy/backup.sh` (TASKS2.md, п. 22), а не однострочник:
он пишет дамп во временный файл, проверяет его (`pg_restore --list`,
минимальный размер) и ротирует по `RETENTION_DAYS`; при битом дампе —
ненулевой код, cron его заметит. Настройки — переменные окружения
(`POSTGRES_HOST/PORT/USER/PASSWORD/DB`, `BACKUP_DIR`, `RETENTION_DAYS`;
для dev-баз — `SQLITE_PATH`).

У compose-сервиса `db` порт наружу не торчит, поэтому на сервере скрипт
удобно запускать одноразовым контейнером с сетью проекта (образ
`postgres:16` — debian, в нём есть и bash, и клиентские утилиты):

```bash
# /usr/local/bin/statcab-backup.sh
docker run --rm \
  --network statcab_default \
  -v /opt/statcab/deploy:/opt/statcab/deploy:ro \
  -v /var/backups/statcab:/var/backups/statcab \
  -e POSTGRES_HOST=db -e POSTGRES_USER=statcab -e POSTGRES_DB=statcab \
  -e POSTGRES_PASSWORD='тот же, что у compose-сервиса db (файл секретов deploy.sh)' \
  -e BACKUP_DIR=/var/backups/statcab -e RETENTION_DAYS=14 \
  postgres:16 bash /opt/statcab/deploy/backup.sh
```

Проверить без записи дампа: тот же запуск с `-e DRY_RUN=1` перед командой.
cron: `15 3 * * * root /usr/local/bin/statcab-backup.sh`.
Плюс том `statcab_data` (загруженные .xlsm, файлы плана) — бэкапить целиком:
`docker run --rm -v statcab_statcab_data:/d -v /var/backups/statcab:/b alpine tar czf /b/data-$(date +%F).tgz -C /d .`

Восстановление (дамп — custom-format в gzip; на живой базе предварительно
остановить backend, `--clean` пересоздаёт объекты). `pg_restore` читает TOC из
конца архива, поэтому подаём файл, а не pipe:

```bash
gunzip -c statcab-pg-<штамп>.dump.gz > /tmp/statcab.dump
docker compose cp /tmp/statcab.dump db:/tmp/statcab.dump
docker compose exec -T db pg_restore -U statcab -d statcab --clean --if-exists /tmp/statcab.dump
docker compose exec -T db rm /tmp/statcab.dump
```

## 7. Обновление версии

```bash
# распаковать новый архив поверх (или git pull)
cd /opt/statcab          # ← та же папка, откуда запускали в первый раз
./deploy.sh --check      # проверки: секреты, пароль к тому pgdata, чужие тома
./deploy.sh              # пересоберёт изменённые образы, БД в томе не тронется
```

Схема БД дополнится на старте сама. Перед обновлением — бэкап из §6.

Дорожка через `git pull` защищена CI (`.github/workflows/ci.yml`, TASKS2.md п. 23):
на каждый push/PR гоняются pytest бэкенда (на SQLite, PostgreSQL не нужен) и
сборка фронта (`tsc -b` + `vite build`) — с красной сборки не выкатываем.
Дорожка через архив: `pack_release.ps1` кладёт `RELEASE-INFO.txt` (версия, ветка,
коммит, время сборки) внутрь архива, а рядом с архивом оставляет его копию и
хеш `<архив>.zip.sha256` уже в unix-формате — после пересылки на сервер
проверять целостность `sha256sum -c statcab-<…>.zip.sha256` до распаковки.

Папка та же, откуда запускали, — так проще, хотя имя compose-проекта зафиксировано
в `docker-compose.yml` (`name: statcab`) и том `statcab_pgdata` один на все запуски:
из другой папки поднимется тот же том, а не пустая база рядом. Обратная сторона
фиксации: на одном docker-хосте не может быть двух разных кабинетов с именем
проекта `statcab` — второй запуск подменит собой первый (те же тома и контейнеры).
Тома `<имя_папки>_pgdata` времён до фиксации имени `deploy.sh` находит и
предупреждает заранее.

Если после обновления кабинет отдаёт 502 на `/api/...` или в логе бэкенда
`password authentication failed for user "statcab"` — пароль в файле секретов разошёлся
с паролем уже инициализированного тома. `./deploy.sh` замечает это до сборки и чинит
сам (`ALTER USER`, том с данными не трогается); посмотреть без изменений — `--check`,
отключить починку — `--no-auto-fix`. Разбор симптомов — `DEPLOY.md`, §7.
`docker compose down -v` не делать: флаг `-v` удаляет тома вместе с данными.

## 8. Данные 1С и «Отчёта диспетчера»

- Витрина складов: `ONE_C_SOURCE=http` + `ONE_C_BASE_URL/LOGIN/PASSWORD`,
  синк по расписанию (`SYNC_INTERVAL_MINUTES`) или push из 1С на
  `/api/onec/push` с `X-OneC-Token: $ONEC_PUSH_TOKEN`.
- Отчёт диспетчера: путь к .xlsm в админке (или `DISPATCHER_XLSM_PATH`);
  файл должен лежать внутри тома `statcab_data` (`/app/data/...`),
  либо грузить руками через админку.
- `SEED_DEMO_DATA=false` в проде — демо-строки не нужны.

## 9. Когда пользователей станет больше

1. **до ~50**: поднять воркеры uvicorn — `UVICORN_WORKERS` в `.env` (при выкате
   через `deploy.sh` — в файле секретов), затем
   `docker compose up -d backend` (образ не пересобирается, контейнер
   пересоздастся с новым окружением). Ориентир — формула из `.env.example`:
   `min(2 × vCPU + 1, max_connections PostgreSQL / (DB_POOL_SIZE + DB_MAX_OVERFLOW))`;
   по умолчанию воркер один — планировщик и блокировка синхронизации живут
   внутри процесса. Смотрят при этом в `docker stats --no-stream`: агрегацию
   «Статистики» считает Python c GIL, поэтому воркеров больше, чем ядер,
   смысла нет: это очередь за CPU, а не параллельность. Сервер — 4 vCPU/8 ГБ.
2. **пул соединений** считают не от числа людей, а от потолка PostgreSQL:

   `воркеры × (DB_POOL_SIZE + DB_MAX_OVERFLOW) ≤ max_connections`

   (`SHOW max_connections;` — по умолчанию 100). Дефолт кабинета —
   1 × (10 + 20) = 30, запас до сотни есть. Девять воркеров с дефолтным
   пулом дают уже 270: PostgreSQL ответит `FATAL: too many connections`, и
   чаще всего — под нагрузкой. Значит, либо воркеров меньше, либо пул
   меньше: 4 × (10 + 10) = 80 — уже впритык. Сам `max_connections`
   поднимать можно, но каждое соединение стоит памяти сервера; выше ~200
   правильнее pgbouncer, а не новые коннекты. Если между кабинетом и базой
   стоит pooler или файрвол, рвущий простые соединения, уменьшают
   `DB_POOL_RECYCLE_SEC` (по умолчанию 1800 с).
3. **~100+**: Postgres на отдельный хост, заглянуть в `EXPLAIN` самых
   тяжёлых агрегатов `services/dispatcher.py`.
4. **дальше**: read-реплики/кэш агрегатов. Для 10 человек всё это не нужно.

## 11. Смена базы и перезапуск из браузера (TASKS2.md, п. 26–28)

Вкладка «База данных» в админке — это `DATABASE_URL` под рукой администратора:
хост, порт, пользователь, пароль и имя базы правятся в форме, а не в `.env` на
сервере. Порядок действий такой же, как с любым чужим сервером: сначала
проверка, потом применение.

1. **«Проверить соединение»** — отдельное соединение и `SELECT 1`, кабинет не
   меняется. Ошибка приходит текстом в то же окно; пароль в неё не попадает
   (наружу идёт маска `***` и флаг «пароль задан»).
2. **«Применить»** — переезд без перезапуска процесса: новый `Engine` собирается,
   проверяется, на нём поднимается схема, и только затем прежний закрывается.
   Не ответила или не хватило прав на DDL — 400 с причиной, кабинет остаётся на
   прежней базе. Начатые в эту секунду запросы падают, а текущий вход администратора
   перестаёт действовать: пользователей знает новая база, поэтому входить придётся
   заново. Об этом говорит подтверждение кнопки. Пустая база (новый кластер,
   свежий файл sqlite) без входа не останется: администратор заводится на ней из
   `ADMIN_LOGIN`/`ADMIN_PASSWORD`, а если пароль в окружении не задан — с
   временным, который печатается в лог.
3. **«Вернуть ENV»** — откат к `DATABASE_URL` из окружения. Если прежняя база уже
   не отвечает, кнопка не всесильна: она лишь снимает указатель, а на прежнюю базу
   процесс вернётся при следующем старте — жмите «Перезапустить сервис» или
   `docker compose restart backend`.
4. **«Перезапустить сервис»** — процесс завершается, супервизор (Docker
   `restart: unless-stopped`, systemd `Restart=always`) поднимает его заново.
   Пока идёт загрузка витрины или импорт отчёта диспетчера, кнопка даёт 409:
   рвать работу посередине нельзя.

Куда что пишется:

- части подключения живут в таблице `app_settings` (`db.host`, `db.port`,
  `db.user`, `db.password`, `db.database`, `db.use_settings`) — то есть в той базе,
  из которой админ пришёл. Это и есть «указатель»: при старте кабинет
  подключается к `DATABASE_URL`, читает указатель и продолжает путь уже на другой
  базе. Bootstrap-база обязана оставаться доступной, иначе указатель не прочитать;
  поэтому `DATABASE_URL` из окружения — точка отката, а не пережиток.
- пароль в ответах API не появляется ни в одном виде; в аудит идут маска URL и
  действие (`admin.db_test`, `admin.db_apply`, `admin.db_revert`,
  `admin.service_restart`).
- после смены базы задание синхронизации пересоздаётся: интервал читается из
  настроек новой базы.
- доступ — JWT, и в нём есть отпечаток базы (`db`): выдаётся под ту базу, к которой
  кабинет подключён. Переехали — прежние токены сами перестали действовать, их не
  надо нигде чистить; refresh-токены к тому же лежат в прежней базе.

Практика: перед первым «Применить» — бэкап (§6). Работает на PostgreSQL и на
sqlite-файле; для PostgreSQL драйвер (`psycopg2-binary`) берётся из
`requirements-prod.txt`, он в образе есть.
