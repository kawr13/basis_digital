# 06. Деплой на сервер (расчёт на ~10 одновременных пользователей)

Кабинет уже упакован в Docker Compose: `db` (PostgreSQL 16) + `backend`
(FastAPI/uvicorn) + `web` (nginx: SPA + прокси `/api`). Ручной сборки не нужно.

---

## 1. Хватит ли сервера на 10 человек — да, с запасом

| Ресурс | Минимум | Комфортно |
|---|---|---|
| CPU | 2 vCPU | 4 vCPU |
| RAM | 4 ГБ | 8 ГБ |
| Диск | 40 ГБ SSD | 80 ГБ (под бэкапы и .xlsm) |
| ОС | Ubuntu 22.04/24.04 LTS, Debian 12 | + Docker Engine + compose plugin |

Запас прочности: uvicorn работает в 2 воркера (переменная `UVICORN_WORKERS`),
у каждого свой пул SQLAlchemy 10+20 соединений → максимум 60 подключений к
Postgres при штатных 100. Десять диспетчеров, открывающих дашборды раз в
минуту, дадут единицы RPS — узкое место наступит ориентировочно после
50+ активных пользователей (см. §9).

## 2. Собрать и загрузить архив

С рабочей машины (Windows):

```powershell
cd D:\basis\statcab
powershell -ExecutionPolicy Bypass -File .\pack_release.ps1
# → release\statcab-<stamp>.zip (без node_modules, .git, .env, локальных БД)
```

Донести до сервера (scp/winscp/git push — что принято):

```bash
scp release\statcab-*.zip user@server:/tmp/
ssh user@server
sudo mkdir -p /opt/statcab && sudo tar -xf /tmp/statcab-*.zip -C /opt/statcab --strip-components=1
# или unzip; внутри должен лежать docker-compose.yml
```

Альтернатива архиву — git: `git clone` на сервер и `git pull` для обновлений.
Архив удобнее, когда сервер без доступа к репозиторию.

## 3. Настроить окружение

```bash
cd /opt/statcab
cp .env.example .env
openssl rand -hex 32   # → SECRET_KEY
openssl rand -hex 16   # → POSTGRES_PASSWORD
$EDITOR .env
```

Обязательно заполнить: `POSTGRES_PASSWORD`, `SECRET_KEY`, `ADMIN_PASSWORD`
(если оставить пустым — случайный пароль напечатает в лог при первом запуске).

**Главный развилочный флаг — `COOKIE_SECURE`:**

| Доступ к кабинету | COOKIE_SECURE |
|---|---|
| HTTPS (домен/сертификат) | оставить пустым (авто: Secure) |
| Внутренний сервер по `http://IP:порт` | `false` |

Если при `ENVIRONMENT=prod` и пустом флаге заходить по http — браузер не
примет refresh-cookie, и пользователей будет выкидывать каждые
`ACCESS_TOKEN_TTL_MINUTES` (30 мин). Это не ошибка входа, а именно флаг.

`CORS_ORIGINS` можно не трогать, если фронт и API идут через один nginx
(один origin). Отдельный домен для фронта — вписать его адрес.

## 4. Запуск

```bash
cd /opt/statcab
docker compose up -d --build        # первая сборка ~5 минут
docker compose logs backend | grep -i админ   # пароль админа, если не задан
curl -s http://localhost:8080/healthz         # → ok
```

Открыть `http://<сервер>:8080`, войти под `admin`, сменить пароль.
Таблицы создаются автоматически при старте (`init_db`), миграции колонок —
тоже (`_ADDED_COLUMNS` в `db.py`).

Файрвол: наружу торчит только `WEB_PORT` (8080). Postgres и backend внутри
compose-сети, наружу не опубликованы — так и оставить.

## 5. Доменное имя, nginx и HTTPS

Общее для всех вариантов:

1. **DNS**: A-запись `cab.example.ru` → IP сервера (в интранете — внутренняя
   DNS-зона или `hosts` на машинах пользователей).
2. **Порты**: снаружи 80 и 443; порт кабинета 8080 наружу лучше не отдавать —
   прокси-оверрайды ниже сами прячут его на `127.0.0.1`.
3. **`.env`**: `CORS_ORIGINS=https://cab.example.ru`, `COOKIE_SECURE=` оставить
   пустым (авто: Secure — при HTTPS это то, что нужно).
4. **`X-Forwarded-For` обязателен**: тротлинг входа (`login_throttle_per_ip`)
   и AuditLog берут IP из этого заголовка. Не передаст внешний прокси —
   все 10 человек окажутся одним «127.0.0.1»: лимит 20 входов/мин делится
   на всех, аудит бесполезен. В примерах ниже заголовки уже проставлены.

Внутренний nginx кабинета сам раскладывает `/api` → backend, `/` → SPA —
внешний проксирует на него **всё одним upstream**, дублировать маршруты не надо.

### 5.1 На сервере уже стоит nginx (классика)

```bash
# 1) кабинет слушает только localhost
docker compose -f docker-compose.yml -f deploy/nginx/docker-compose.host-nginx.yml up -d

# 2) vhost (шаблон deploy/nginx/statcab.vhost.conf, поправить server_name)
sudo cp deploy/nginx/statcab.vhost.conf /etc/nginx/sites-available/statcab
sudo ln -s /etc/nginx/sites-available/statcab /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 3) сертификат Let's Encrypt (допишет ssl-блок сам)
sudo certbot --nginx -d cab.example.ru
```

### 5.2 nginx на хосте не нужен — Caddy внутри Docker (сертификаты сам)

```bash
# правка deploy/caddy/Caddyfile: свой домен вместо cab.example.ru
docker compose -f docker-compose.yml -f deploy/caddy/docker-compose.caddy.yml up -d
docker compose logs caddy        # выпуск сертификата с первого раза может занять минуту
```

Caddy выпускает и продлевает Let's Encrypt автоматически — нужен только
доступ из интернета на 80/443. Внутри compose он доходит до `web:80`,
наружу кабинет не торчит вообще.

### 5.3 Внутренний домен без доступа из интернета

Публичный сертификат Let's Encrypt получить нельзя (домен не виден снаружи).
Варианты, от лучшего к простому:

- **Свой корпоративный CA** — выпустить сертификат на `cab.internal`,
  корневой сертификат раздать на машины (GPO) — HTTPS как у людей.
- **Self-signed** + добавление сертификата в доверенные — работает, но
  противно администрировать.
- **Просто `http://cab.internal`** — тогда в `.env` `COOKIE_SECURE=false`
  (см. §3) и доступ по firewall только из подсети офиса.

### 5.4 gzip для API и размер тела запроса

nginx проксируемые ответы по умолчанию **не сжимает**: `gzip on` и
`gzip_types application/json` работают только на статику, а весь API — это
`proxy_pass` (годовое `overview` шло 743 КБ вместо ~60 КБ). Выключатель —
`gzip_proxied any;`, и он нужен в обоих конфигах: внутреннем и внешнем
(иногда vhost остаётся единственным nginx, §5.1). Там же `client_max_body_size
16m`: «Отчёт диспетчера» едет из браузера в base64 (+33 % к весу), при 2m
nginx отвечал 413 ещё до кода приложения.


## 6. Бэкапы (настроить в первый же день)

```bash
# /usr/local/bin/statcab-backup.sh
docker compose -f /opt/statcab/docker-compose.yml exec -T db \
  pg_dump -U statcab statcab | gzip > /var/backups/statcab/statcab-$(date +%F).sql.gz
find /var/backups/statcab -name '*.sql.gz' -mtime +14 -delete
```

cron: `15 3 * * * root /usr/local/bin/statcab-backup.sh`.
Плюс том `statcab_data` (загруженные .xlsm, файлы плана) — бэкапить целиком:
`docker run --rm -v statcab_statcab_data:/d -v /var/backups/statcab:/b alpine tar czf /b/data-$(date +%F).tgz -C /d .`

Восстановление: `gunzip -c dump.sql.gz | docker compose exec -T db psql -U statcab statcab`.

## 7. Обновление версии

```bash
# распаковать новый архив поверх (или git pull)
cd /opt/statcab
docker compose up -d --build   # пересоберёт изменённые образы, БД в томе не тронется
```

Схема БД дополнится на старте сама. Перед обновлением — бэкап из §6.

## 8. Данные 1С и «Отчёта диспетчера»

- Витрина складов: `ONE_C_SOURCE=http` + `ONE_C_BASE_URL/LOGIN/PASSWORD`,
  синк по расписанию (`SYNC_INTERVAL_MINUTES`) или push из 1С на
  `/api/onec/push` с `X-OneC-Token: $ONEC_PUSH_TOKEN`.
- Отчёт диспетчера: путь к .xlsm в админке (или `DISPATCHER_XLSM_PATH`);
  файл должен лежать внутри тома `statcab_data` (`/app/data/...`),
  либо грузить руками через админку.
- `SEED_DEMO_DATA=false` в проде — демо-строки не нужны.

## 9. Когда пользователей станет больше

1. **до ~50**: поднять воркеры uvicorn — `UVICORN_WORKERS` в `.env`, затем
   `docker compose up -d backend` (образ не пересобирается, контейнер
   пересоздастся с новым окружением). Ориентир — `воркеров ≈ 2 × vCPU + 1`:
   правило работает для смешанной нагрузки, где запрос часть времени ждёт
   базу. Смотрят при этом в `docker stats --no-stream`: агрегацию
   «Статистики» считает Python c GIL, поэтому воркеров больше, чем ядер,
   смысла нет: это очередь за CPU, а не параллельность. Сервер — 4 vCPU/8 ГБ.
2. **пул соединений** считают не от числа людей, а от потолка PostgreSQL:

   `воркеры × (DB_POOL_SIZE + DB_MAX_OVERFLOW) ≤ max_connections`

   (`SHOW max_connections;` — по умолчанию 100). Дефолт кабинета —
   2 × (10 + 20) = 60, запас до сотни есть. Девять воркеров по формуле из
   п. 1 дают уже 270: PostgreSQL ответит `FATAL: too many connections`, и
   чаще всего — под нагрузкой. Значит, либо воркеров меньше, либо пул
   меньше: 4 × (10 + 10) = 80 — уже впритык. Сам `max_connections`
   поднимать можно, но каждое соединение стоит памяти сервера; выше ~200
   правильнее pgbouncer, а не новые коннекты. Если между кабинетом и базой
   стоит pooler или файрвол, рвущий простые соединения, уменьшают
   `DB_POOL_RECYCLE_SEC` (по умолчанию 1800 с).
3. **~100+**: Postgres на отдельный хост, заглянуть в `EXPLAIN` самых
   тяжёлых агрегатов `services/dispatcher.py`.
4. **дальше**: read-реплики/кэш агрегатов. Для 10 человек всё это не нужно.

## 10. Чек-лист перед сдачей в эксплуатацию

- [ ] `SECRET_KEY`, `POSTGRES_PASSWORD`, `ADMIN_PASSWORD` — сгенерированы, не из примера
- [ ] `.env` не лежит в git и не уехал в архиве (`.gitignore` бережёт)
- [ ] `COOKIE_SECURE` соответствует http/https
- [ ] `/healthz` отвечает, логи `docker compose logs` чистые
- [ ] админ сменил пароль после первого входа
- [ ] бэкап-крон работает (проверить: дамп реально создаётся и читается)
- [ ] демо-пользователей/данных нет (`SEED_DEMO_DATA=false`)
- [ ] наружу открыт только WEB_PORT, Postgres — нет
