# Постановка судов

Ручной планировочный документ «План постановки судов» — электронный аналог того плана,
который сейчас ведут в Excel (`26 05 ПОСТАНОВКА.xlsx`).

## Чем это отличается от остального кабинета

| | витрина статистики | постановка судов |
|---|---|---|
| кто создаёт | коннектор 1С (только чтение) | диспетчер руками |
| таблицы | `fact_*` | `berths`, `vessel_placements` |
| перезапись | каждое окно синхронизации | только пользователь из UI |
| права | все читают | настраивается: `vessels.view_roles` / `edit_roles` / `delete_roles` |

## Как устроено время

Сутки разбиты на **4 слота по 6 часов** — `00-06`, `06-12`, `12-18`, `18-00`, ровно
как в исходном плане. Постановка хранит `starts_at` и `ends_at` — **начало первого и
последнего занятого слота**, границы включительные. Поэтому:

* время обязательно кратно слоту (07:15 не примём);
* «посмотреть любой период» работает и для судов, начатых раньше: в выборку попадает
  всё, что задевает период хотя бы одним слотом, а вылезание за край периода показывается
  пунктирным краем полосы.

## Как устроена длина

Второе измерение плана — **длина причала, сверху вниз**. Одна ячейка = **10 метров**:
причал 100 м — это 10 ячеек, 130 м — 13. Судно занимает отрезок длины:

```
offset_m   отметка швартовки, метры от начала причала
length_m   длина судна, м
```

Отсюда правила:

* два судна у одного причала мешают друг другу, только если пересекаются **и по
  времени, и по метрам**. `409` говорит прямо: «Причал РП-3: уже стоит "CROWN SAPPHIRE"
  (10.05 00:00 — 12.05 12:00, 0–70 м), пересечение по длине 40–70 м»;
* судно не может вылезти за край причала: `length_m > length_m причала` или
  `offset_m + length_m > length_m причала` → `400` («Судно 140 м не встанет у причала
  РП-1: длина причала 100 м»);
* `length_m = NULL` — длина не задана: считаем, что судно перекрывает причал до конца,
  и оно конфликтует со всем, что стоит рядом по времени. Молча разрешить вторую
  постановку было бы хуже;
* без длины нельзя поставить судно не с начала причала — непонятно, сколько занято.

Раньше вместо метров был счётчик «дорожек» (`lanes` / `lane`). Он остался в базе
(старые строки никуда не делись), но на проверку конфликта больше не влияет: шкала
стала метровой, и она честнее — два судна по 70 м на 100-метровом причале «две дорожки»
пропустили бы, а метры не пропускают.

## Модель

```
berths             причал: code (РП-1), depth (осадка, м), length_m (метраж, м), sort_order, is_active,
                   length_cells (сколько ячеек по 10 м, считает бэкенд)
vessel_placements  строка плана: berth_id, offset_m, length_m, vessel, volume, cargo, note,
                   starts_at, ends_at, created_by/updated_by, created_at/updated_at,
                   lane (устарело, сохраняется для старых строк)
```

Справочник причалов при первом запуске заполняется типовыми РП-1…РП-6 (метраж 100–130 м) —
дальше его ведёт администратор.

## Кто что может (настраивается в админке)

Настройки на вкладке «Настройки», значения — списки ролей через запятую:

| настройка | по умолчанию | что закрывает |
|---|---|---|
| `vessels.view_roles` | `admin,top,manager` | просмотр плана и справочника причалов; без права пропадает вкладка и маршрут `/vessels` |
| `vessels.edit_roles` | `admin,top` | создание и правку постановок |
| `vessels.delete_roles` | `admin` | удаление строк |

Неизвестную роль в настройку не пускают (422), пустой список тоже — план не может остаться
без владельцев. Фронт берёт эти же значения из `/api/settings/public`, поэтому кнопки
не расходятся с правами API.

### Право для конкретного человека

Роли — это про всех сразу. Когда нужен один человек (диспетчер Петров — менеджер, но план
ведёт он), право ставят прямо в карточке пользователя: Администрирование → Пользователи →
«Постановка судов». Графа `users.vessel_right`, значения:

| значение | что умеет |
|---|---|
| пусто | по роли, то есть правила из таблицы выше |
| `none` | не видит ни плана, ни вкладки |
| `view` | только смотреть |
| `edit` | смотреть + ставить и править |
| `manage` | смотреть + править + удалять |

Личная графа перекрывает ролевые настройки в обе стороны: `none` закрывает даже
администратора, `edit` открывает менеджеру то, что ролью ему не положено. Считается в
`app/services/vessels.py::rights_for` (бэкенд) и в `src/settings.ts::resolveVesselRights`
(фронт) — правила там одинаковые. Право меняется без перелогина: оно приходит в ответе
входа вместе с пользователем, а карточку сохраняет админ.

Право на документ не спорит с доступом к разделу: если «Постановка» снята в личных
вкладках человека (`users.sections`, галки «Вкладки» в его карточке) либо раздел скрыт
для всех (`ui.hidden_sections`), план закрыт целиком — и просмотр, и постановка.
Эти правила считает `app/services/sections.py`, и они только сужают доступ: `manage`
не вернёт раздел, который человеку не выставлен.

### Почему права приезжают с пользователем

Со входа и с `/api/auth/me` уходит ещё и посчитанный набор — `vessel_rights:
{view, edit, delete}`. Фронт прячет вкладку «Постановка» и кнопку «Новая постановка» по ним,
не дожидаясь `/api/settings/public`: иначе запрещённая вкладка успевает мигнуть на первом
кадре, а если запрос настроек недоступен — остаётся навсегда. Ответ бэкенда при этом был
403 и раньше: показывать лишнюю кнопку было нельзя в любом случае. Когда админ меняет право,
у уже открытой вкладки оно применяется при возврате к окну — `AuthProvider` тянет `/me` на
`visibilitychange`/`focus`.

## API

| метод | что |
|---|---|
| `GET /api/vessels/berths` | справочник причалов (администратор — всегда, остальным по праву `view`) |
| `POST` / `PATCH /api/vessels/berths[/{id}]` | причалы (admin) |
| `DELETE /api/vessels/berths/{id}` | удалить причал, если на нём нет ни одной постановки (admin); иначе `409` с подсказкой снять с линии |
| `GET /api/vessels/placements?from&to&berth_id` | сетка плана за период |
| `GET /api/vessels/free-offset?berth_id&starts_at&ends_at&length_m` | первая свободная отметка (м) для судна такой длины — подсказка в форме |
| `POST` / `PATCH /api/vessels/placements[/{id}]` | строка плана (admin, top) |
| `DELETE /api/vessels/placements/{id}` | удаление строки (admin), факт уходит в журнал аудита |
| `GET /api/vessels/plan.pdf?from&to&day_from&day_to&berth_ids` | PDF **видимой области** плана: окно присылает фронт, сервер рисует вектором |

## Экран

Сетка читается как лист миллиметровки: слева направо — время, сверху вниз — метры
причала. У каждого причала свой блок: строка с его метражом, затем линейка с отметками
каждых 10 м, справа — поле, где полоса судна стоит ровно на своих метрах. Ячейка сжата
до 12 px (10 м): 60-метровое судно — это 72 px, а не 108, поэтому на экран влезает
вдвое больше причалов. Из-за этого подписи на линейке стоят через одну (каждые 20 м),
иначе цифры сливаются. Длину не задали — полоса идёт до конца причала.

Панель периода (пресеты «Неделя / 2 недели / Месяц», два поля даты, «Обновить»,
«Новая постановка», «✏ Корректировка») живёт внутри плашки с планом, начинается у её левого
края и собрана компактно (`.btn-mini`, `.field-mini`). В шапке эти кнопки уезжали в правый
угол к «Выйти» и были крупнее, а план читают слева направо — управление должно стоять там
же, где начинается таблица. Кнопка «Новая постановка» показывается только тем, у кого есть
право `edit`, вкладка «Постановка» — только тем, у кого есть `view`.

### Стрелки перешвартовок

Цепочка из нескольких перестановок одного судна — это несколько стрелок одного
цвета, и без подписей она читается как «паутина»: непонятно, какая линия куда
ведёт. Экран обязан говорить то же самое теми же словами, что и лист (см.
«Стрелки через границу листа»):

* у наконечника — подпись `шаг N→M · причал · дд.мм чч:мм` (если цель —
  карман, вместо шифра причала слово `Ожидание`), тем же цветом, что стрелка, и
  с белой обводкой, чтобы читаться поверх сетки и серых выходных;
* номера шагов считает `chainSteps` (`src/vessels.ts`) — та же логика, что у
  `_chain_steps` в `app/services/plan_pdf.py`, поэтому «шаг 2» на экране и на
  бумаге — одна и та же перестановка;
* кружок на старте стрелки и наконечник на конце: направление читается даже в
  чёрно-белой печати и там, где подпись не влезла в кадр;
* наведение на полосу (а на мобильном — открытая карточка, hover там нет)
  оставляет яркими стрелки этой цепочки, чужие гаснут до 15%, а полоса-оригинал
  и полоса-цель получают рамку цвета своей стрелки — это ответ на «откуда»;
* стрелка — прямая «из А в Б»: от ближнего торца оригинала к ближнему торцу
  копии. Ортогональную «ёлочку» убрали: на сетке причалов она резала чужие
  строки, и стрелки разных цепочек путались. Подпись ставится над наконечником
  (у правого края — слева от него), поэтому она не заставляет холст листаться
  шире, чем он листался до неё.

## Перетаскивание мышью (WYSIWYG)

«✏ Корректировка» в правом конце панели периода включает режим перетаскивания: полосы
становятся ручками. Тянуть горизонтально — время (шаг один слот = 6 часов), тянуть
вертикально — место у причала (шаг 5 м). Отпустили — PATCH ушёл на сервер, сетка
перерисовалась. Создание по-прежнему только через окно постановки: при перетаскивании
легко потерять контроль над длиной и временем, а окно показывает, куда встанет судно,
до того как строка появилась.

Почему это вообще возможно без потери точности: шаг перетаскивания ровно равен шагу
хранения. Слот — минимальная единица времени в модели, 5 м — половина ячейки шкалы.
Полоса во время перетаскивания подсвечивается и стоит на «посадочных» отметках, а не там,
где курсор: промежуточных значений не бывает.

Что бэкенд не пустит:

* перетаскивание за границы выбранного периода — отсекаем на клиенте («Судно нельзя
  вынести за границы выбранного периода»), иначе полоса просто исчезнет из вида;
* наезд на другое судно по метрам и времени — обычный `409` с текстом про пересечение,
  после отказа полоса возвращается на свою отметку (перезагрузка плана);
* выход за край причала — `offset_m` ограничиваем на клиенте, бэкенд перепроверяет.

Стрелки на клавиатуре двигают полосу под фокусом (влево/вправо — слот, вверх/вниз — 5 м):
тем, кому мышью попадать в полосу шириной 12 px неудобно. Клик по полосе после
перетаскивания карточку не открывает — иначе любое перемещение заканчивалось бы модалкой.

Режим включается только при праве `edit` и выключается тем же карандашом: без него
полоса снова просто кнопка, открывающая карточку.

### Судно можно перевести на другой причал

Перетаскивание не ограничено одним причалом: под курсором ищется **поле шкалы**
причала (`[data-berth-scale]`), и если курсор оказался в чужом поле, судно уезжает
туда. Отметка швартовки берется из причала-цели, а не «дельтой от старта» — иначе
переезд на причал другой длины ломался бы арифметикой. Причал-цель подсвечивается,
пока над ним курсор.

Мерить нужно именно поле шкалы, а не блок причала целиком: у блока сверху строка с
названием и метражом, и отсчёт метров от её верха съезжает на полтора десятка
метров. Это ровно та ошибка, которую легко вернуть.

Дальше работает та же проверка, что и при создании: `PATCH` с новым `berth_id`
проходит `validate()` — на новом причале судно может не влезть в метраж или наехать
на соседнее, и бэкенд ответит `409` с текстом, где именно.

### Ширина поля

Слот по горизонтали больше не зашит: его ширина считается от реальной ширины
контейнера (`ResizeObserver`), поэтому недельный и двухнедельный периоды тянутся от
левой границы до правой. На 1600px слот становится ~49 px вместо 33. Месяц (124
слота) в любую ширину не влезает — там включается прокрутка, и слот держит минимум
22 px, при котором ещё читается «00».

Ширина дробная намеренно: округление до целых пикселей оставляет справа незаполненную
полосу шириной до половины слота.

### PDF: в лист уходит видимая область, а не весь период

Кнопка «⤓ PDF» скачивает файл, который нарисовал бэкенд (`app/services/plan_pdf.py`,
reportlab). Печатью браузера это делать перестали: диспетчеру нужен файл с конкретным
куском плана, а не страница кабинета в диалоге печати, где шапка и панель периода
уезжают на другой лист. Картинкой (html2canvas) тоже нельзя — план обязан оставаться
текстом: кириллица, поиск, копирование.

**Кто решает, что рисовать.** Фронтенд — только он знает, что сейчас в кадре. В момент
нажатия берутся `scrollLeft`/`clientWidth` → сутки окна и пересечение прямоугольников
блоков → причалы; уезжает это в `GET /api/vessels/plan.pdf?from&to&day_from&day_to&berth_ids`.
Сервер про кадр ничего не знает и сам не догадывается: рисует ровно то, что попросили,
проверяя только право `view`. Границы считаются в момент нажатия, поэтому лист честен
относительно того, что пользователь видел секунду назад.

Сутки берутся **целиком** (половину суток в лист класть нельзя), причалы — **целыми
блоками**, даже если в кадре видна их часть. Постановка, выходящая за границу кадра,
обрезается и с этой стороны дорисовывается пунктиром — тот же приём, что у постановок,
начатых раньше периода. Лист — альбомный A4, поля 8 мм; ширина слота считается от
листа (`ширина_поля / слотов_в_окне`), поэтому правый край не отрезается и пустая
полоса справа не остаётся: сколько суток попросили, столько и растянули.

Месяц в окно не влезает, поэтому печать всего периода означала бы сжатие до нечитаемого
кегля. Кадр даёт крупный лист, а следующий кусок получают так же: прокрутил сетку →
«⤓ PDF».

**Лист сжимается, а не режется.** Даты окна — шапка таблицы, а не шапка причала,
поэтому они печатаются **один раз на лист**, над первым его блоком. Строка
метража причала уплотнена (10 точек вместо 16), зазор между блоками — 3 точки,
а метровая шкала имеет право сжиматься с 10 точек на 10 м вплоть до 3,5 — ниже
подпись судна в полосе перестала бы читаться (шаги подписей линейки при этом
растут, а отметки остаются). Типовое окно из шести причалов после этого лежит на
одном листе, и стрелки перешвартовок вовсе не пересекают границу листа. Не
влезло и при поле шкалы — план распадается на листы ровно как раньше, со всеми
огрызками `· лист N` и `· вне кадра`: компактность не отнимает fallback. О сжатии
листа говорит сноска внизу. Подпись судна из низкой полосы не вылезает — не
влезла, значит не нарисована (снаружи полосы подписей не бывает).

**Почему это не вторая вёрстка плана.** Лист рисуется вектором по тем же данным и тем
же правилам, что и сетка (`slots_in_range`, `span_of`, та же палитра грузов, что в
`src/vessels.ts`). Причал между страницами не разрезается: блок целиком уходит на
следующий лист, а шапка листа с датами окна и сноска повторяются на каждом листе
(шапка суток при этом одна на лист) — листы распечатывают и по одному.

**Стрелки через границу листа и за край кадра.** Лист разрезан по причалам и
суткам, и пара «оригинал → копия» может оказаться на разных листах — или
наполовину вне кадра. Правило одно для всех случаев: **если в кадре есть
хотя бы одна ПОЛОСА связи, на бумаге обязана быть подпись `шаг N→M` с теми же
номерами, что на экране**. Второй конец либо на другом листе, либо не печатается
вовсе. Карман «Ожидание» сам по себе поводом не считается: его чипы печатают на
каждом листе, и стрелка от чипа в не напечатанное место смотрела бы в пустоту.

**«Ожидание» — очередь на первые сутки кадра.** Карман печатают на каждом
листе независимо от кадра, и без этого списка план терял бы ждущие суда; но
судно перестаёт ждать в момент, когда начинается его плановое перемещение.
Поэтому список режет **первый** день кадра: если окно начинается уже после того,
как перемещение началось, судно застал его состоявшимся — его чипа на листе нет,
как и обеих его стрелок. Иначе лист вечно рассказывал бы, что «ДОН ждёт РП-1»,
в то время как РП-1 на этом же листе уже занят.

Мерить последними сутками нельзя: цепочка «ДОН» целиком лежит в кадре
26.10 — 13.11, и правило по концу окна съело бы всю перешвартовку — и чип,
и обе стрелки — оставив на бумаге два одиноких судна вместо перестановки.

Раскладка считается в два прохода — сначала «какой причал на каком листе» (там
же рождаются и сами листы), потом рисование, — причём второй проход берёт готовые
числа первого: высота блока считается одной функцией `block_need`, а рисовальщик
ничего не решает сам, поэтому лист и раскладка не могут разойтись ни на точку.
А что рисовать у каждой половины связи, решает одна функция
`_arrow_plan`: она возвращает список дескрипторов `(вид, лист, оригинал, копия,
подпись)`, и ветки больше не разбросаны по `draw_block` и `waiting_section`
(именно так терялся случай «один день в кадре»: ни одна из веток не срабатывала).
Виды огрызков: на листе начала стрелка уходит в нижний край блока причала с
подписью `→ РП-6 · лист 2`, на листе цели входит в полосу со стороны шапки с
подписью `от РП-3 · лист 1`; если второго конца на бумаге нет вообще — тот же
огрызок, но `· вне кадра` (у чипа «Ожидания» огрызок растёт вверх от его
верхней грани, а не вниз, потому что блока у кармана нет). У каждой стрелки —
номер шага в цепочке перешвартовок (по `moved_from_id`, от корня в ширину),
чтобы на распечатке стрелки сводились руками; стрелка в чип «Ожидания» рисуется
в том же направлении, что на экране, — от полосы оригинала к чипу копии.

Номера шагов PDF считает по **полным цепочкам периода** — тем же набором
строк, что отдаёт сетка, — а не по тем, что влезли в лист: копия без оригинала
не имеет права становиться корнем и перенумеровываться. Фильтр причалов
(фронт присылает то, что в кадре) замыкается вдоль цепочки **транзитивно и в
обе стороны**: цепочка из четырёх причалов печатается четырьмя, даже если в
кадре один, — половина стрелки не должна печататься без второй.
Все стрелки листа рисует `arrow_straight`: прямая «из А в Б», кружок на старте
и остриё вдоль самой линии — ровно так же, как на экране. Ортогональную
«ёлочку» убрали с обоих носителей сразу: на сетке причалов она резала чужие
строки, и стрелки разных цепочек приходилось различать глазами.

Сверить бумагу с экраном можно без браузера: `python tools/pdf_arrow_parity.py`
перебирает спорные кадры и фильтры и требует, чтобы множество пар `шаг N→M`
на листе совпадало с экраном (9 случаев; прогон — с поднятым бэкендом).

**Кириллица.** Стандартные Helvetica/Times в PDF кириллицу не рисуют, поэтому
`DejaVuSans.ttf` лежит в репозитории (`app/assets`, свободная лицензия) и идёт первым в
списке поиска шрифта; системные DejaVu/Arial — запасные. Без файла файл бы получился —
просто вместо названий судов были бы пустые места. Тест читает PDF через `pypdf` и
ищет там «СВЕТЛОГОРСК».

**Имя файла** строится по видимому окну (`план_постановки_2026-05-01_2026-05-07.pdf`),
а не по периоду: два разных листа одного месяца иначе назывались бы одинаково.

Посмотреть лист без браузера: из `backend/` — `python ../tools/plan_pdf_preview.py
--day-from 0 --day-to 6`; код тот же, что и за кнопкой.


## Справочник причалов в админке

Вкладка «Администрирование → Причалы»: добавить причал, поправить осадку и метраж,
поменять порядок в плане, снять с линии, удалить.

Длина причала — не справка, а ограничение: из неё сразу считается шкала («130 м — 13
ячеек по 10 м»), и бэкенд не примет судно длиннее. Код проверяется на читаемость
(минимум 2 символа, буквы/цифры/пробел/дефис/слэш): код печатают в плане и по нему
ищут строку.

Два состояния, и они не одно и то же:

* **снят с линии** (`is_active=false`) — причал исчезает из сетки плана и из ответа
  `/api/vessels/placements`, но его постановки остаются в базе и в истории. Так
  причал в ремонте не портит прошлые периоды;
* **удалён** — только если на причале ни одной постановки (`409` иначе). Справочник
  чистят от ошибок ввода, а не переписывают историю.

Порядок сортировки (`sort_order`) задаёт, как причалы идут в плане: меньше — выше.
