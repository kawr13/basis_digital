# 08. Архитектура для руководства

Три вопроса, на которые отвечает этот документ:
1. **nginx — он внутри или снаружи?** (краткий ответ в §2)
2. **Где что запускается: в контейнере или на сервере?** (§1)
3. **Как сделать так, чтобы несколько сервисов пользовались одной базой?** (§4)

---

## Коротко (если читать больше ничего)

Контейнер — это не «виртуальная машина с сервисом внутри», а одна программа.
В нашем проекте в контейнере `web` программой является **nginx**: образ `web` — это
и есть nginx, он запускается вместо стартапа системы и умирает вместе с контейнером.
Второй nginx — **снаружи**, он стоит на самом сервере как обычная системная служба
(`systemctl`) и нужен только для HTTPS и домена. Он необязателен.

База сейчас **заперта внутри своего проекта**: у контейнера `db` не опубликован ни
один порт, и доступ к нему разрешён только соседям по внутренней сети одного
`docker compose`. Подключить к ней второй сервис можно, но для этого базу нужно
явно «вынести» в общий слой — сеть и том объявить внешними, иначе они останутся
собственностью одного проекта. Это делается за вечер, инструкция в §6, и сделать
это лучше **до** объединения, а не после (см. §5, пункт про имена томов — там риск
потерять данные).

## 1. Где что запускается

| Компонент | Где физически работает | Кто его запускает | Порт | Файл конфигурации |
|---|---|---|---|---|
| nginx (внутренний) | **внутри контейнера `web`** | сам контейнер (это его главный процесс) | `80` внутри контейнера | `frontend/nginx.conf` |
| nginx (внешний) | **на сервере, вне Docker** | `systemd` (`systemctl reload nginx`) | `80`, `443` | `deploy/nginx/statcab.vhost.conf` → `/etc/nginx/sites-available/` |
| Caddy (альтернатива внешнему) | в контейнере | compose-файл | `80`, `443` | `deploy/caddy/Caddyfile` |
| Бэкенд (FastAPI/uvicorn) | внутри контейнера `backend` | контейнер (PID 1) | `8000` внутри сети | переменные окружения в `docker-compose.yml` |
| PostgreSQL | внутри контейнера `db` | контейнер | `5432` внутри сети | том `pgdata` |
| Vite dev-сервер | **на рабочей машине, без Docker** | разработчик (`npm run dev`) | `5173` | `frontend/vite.config.ts` |

Схема продакшена целиком:

```
        Интернет / браузер пользователя
                    │
                    │  https://cab.example.ru  (443)
                    ▼
   ═══════════ СЕРВЕР (хост) ═══════════════════════════════════════
   ║                                                              ║
   ║  [СНАРУЖИ Docker]  nginx + TLS-сертификат Let's Encrypt      ║
   ║                    80 → редирект, 443 → прокси на 127.0.0.1:8080
   ║                              │                               ║
   ║ ── Docker ───────────────────┼────────────────────────────── ║
   ║                              ▼                               ║
   ║   ┌───────────────────────────────────────────┐              ║
   ║   │ контейнер web                             │              ║
   ║   │   nginx  ← ВНУТРИ контейнера (образ nginx)│              ║
   ║   │   ├─ /            статика React (dist)    │              ║
   ║   │   ├─ /api/   ─────proxy─────┐             │              ║
   ║   │   └─ /healthz ──proxy──┐    │             │              ║
   ║   └────────────────────────┼────┼─────────────┘              ║
   ║                            ▼    ▼                            ║
   ║   ┌───────────────────────────────────────────┐              ║
   ║   │ контейнер backend  (uvicorn :8000)        │              ║
   ║   └───────────────────────┬───────────────────┘              ║
   ║                           ▼                                  ║
   ║   ┌───────────────────────────────────────────┐              ║
   ║   │ контейнер db  (PostgreSQL 16 :5432)       │              ║
   ║   │   порт НЕ опубликован на хост             │              ║
   ║   └───────────────────────┬───────────────────┘              ║
   ║                           ▼                                  ║
   ║                    том pgdata (диски сервера)                ║
   ╚══════════════════════════════════════════════════════════════╝
```

Наружу из Docker смотрит **один порт**. `backend` и `db` портов наружу не имеют
вовсе — их из интернета невозможно увидеть, даже если фаервол открыт.

## 2. nginx: их два, они разные, это не ошибка

| | **внутренний** | **внешний** |
|---|---|---|
| Что это | образ `nginx:1.27-alpine`, в него положена собранная папка `dist` | обычный nginx, установленный на сервере |
| Где запускается | **внутри контейнера**, это и есть контейнер | **снаружи**, служба сервера |
| Зачем | раздать файлы интерфейса и положить `/api` на бэкенд | домен, HTTPS, сертификат, сжатие |
| Обязателен? | **да**, всегда — без него не отдаётся фронт | нет, нужен только для HTTPS/домена |
| Файл | `frontend/nginx.conf` | `deploy/nginx/statcab.vhost.conf` |
| Ставится | автоматически, при сборке образа | вручную: `cp` в `sites-available` + `certbot` |
| Порт | `80` внутри контейнера → `8080` на сервере | `80`/`443` на сервере |

**Формулировка для отчёта одной строкой:**
> nginx у нас два: один — часть образа интерфейса и работает внутри контейнера
> (раздаёт фронт и проксирует API), второй — обычный серверный nginx снаружи
> контейнеров, он терминирует HTTPS и проксирует на контейнер. Второй опционален:
> вместо него может стоять Caddy внутри Docker, тогда внешнего nginx не нужно.

Когда какой вариант включён:

| Задача | Команда | Внешний nginx | Внутренний nginx |
|---|---|---|---|
| Разработка на ноутбуке | `npm run dev` + `uvicorn` | нет | нет (роль — Vite-прокси) |
| Прод «как есть», по IP | `docker compose up -d` | нет | **есть** |
| Прод с доменом и HTTPS, nginx уже стоит на сервере | `docker compose -f docker-compose.yml -f deploy/nginx/docker-compose.host-nginx.yml up -d` | **есть** | есть |
| Прод с доменом и HTTPS, nginx на сервере ставить не хотим | `docker compose -f docker-compose.yml -f deploy/caddy/docker-compose.caddy.yml up -d` | нет, его делает Caddy-контейнер | есть |

Оба/nginx-варианта описаны подробнее в `docs/06_деплой_на_сервер.md`, §5.

Важная деталь внешнего nginx: он **обязан** передавать `X-Real-IP` и
`X-Forwarded-For`. Без них защита от подбора пароля считает все попытки с одного
`127.0.0.1` (то есть лимит «сваливается» на один адрес), а журнал аудита теряет
реальные IP пользователей.

## 3. Как устроена база сейчас и почему её нельзя подключить «прямо так»

```yaml
# docker-compose.yml, сокращённо
services:
  db:
    image: postgres:16-alpine
    volumes: [ pgdata:/var/lib/postgresql/data ]     # том принадлежит ЭТОМУ проекту
    # ports: нет ни одной строки → наружу порт не опубликован
```

Следствия:

1. Имя `db` разрешается в IP **только внутри сети этого compose-проекта**. Сервис
   из другого проекта (или процесс с хоста) до него не доедет — это не настройка,
   это свойство изоляции compose.
2. Том `pgdata` фактически называется `<имя_проекта>_pgdata`, а имя проекта = имя
   папки, из которой запущен `docker compose`.
3. Версия жёсткая: PostgreSQL **16**. Все будущие соседи должны быть с ней совместны.

Пункт 2 — это не теория. В репозитории сейчас папка называется `statcab`, а
инструкция в `DEPLOY.md` клонирует `basis_digital`. Один и тот же проект, запущенный
из папок с разными именами, получит **разные тома** и поднимет пустую базу рядом со
старой, где останутся данные. Лечится одной строкой (`name:` у тома), см. §6.

## 4. Объединение: как переиспользовать базу несколькими сервисами

Сразу разделим два разных желания, которые часто путают:

- **переиспользовать инстанс PostgreSQL** (один процесс, одна память, один бэкап) —
  правильно и дёшево, так и надо делать;
- **складывать разных сервисов в одну схему/одну учётку** — неправильно: сервисы
  начнут конфликтовать таблицами и ронять друг друга миграциями.

Правильная форма: **один инстанс → по отдельной базе (или схеме) на сервис → у
каждого сервиса своя роль-пользователь со доступом только к своей базе.**

```
PostgreSQL 16 (один контейнер, один pgdata, один бэкап)
├── db_statcab     + роль statcab       ← кабинет статистики
├── db_crm         + роль crm           ← будущий сервис 2
├── db_docs        + роль docs          ← будущий сервис 3
└── db_reports     + роль reports        ← будущий сервис 4
```

### Вариант A. Все сервисы в одном `docker-compose.yml`

Самый быстрый путь, если сервиса два-три и выкатываются они вместе.

```yaml
services:
  db:            { image: postgres:16-alpine, ... }
  backend:       { ... }
  web:           { ... }
  crm-backend:
    build: ./crm/backend
    environment:
      DATABASE_URL: postgresql+psycopg2://crm:${CRM_DB_PASSWORD}@db:5432/db_crm
    depends_on:
      db: { condition: service_healthy }
```

- Плюс: 5 минут работы, `depends_on` работает, одна сеть, один `up -d`.
- Минус: один `docker compose down` валит всё; команда, «сломившая» базу, ломает
  все сервисы сразу; растущий файл и всё более длинная сборка.

### Вариант B (рекомендую). Общий слой-«платформа» + внешние сеть и том

База и вход (nginx/Caddy) вынесены в отдельный проект-«платформу». Прикладные
проекты подключаются к ней через **внешнюю сеть** и больше друг о друге ничего не
знают.

```
deploy/platform/docker-compose.yml   ← postgres, caddy/nginx, общие сеть и том
statcab/docker-compose.yml           ← backend + web        ─┐
crm/docker-compose.yml               ← backend + web         ├ все в сети statcab_net
docs/docker-compose.yml              ← backend + web        ─┘
```

Плюсы: база живёт своей жизнью и переживает удаление/пересборку любого сервиса;
сервисы выкатываются и откатываются независимо; у входа один общий TLS-терминатор
на все домены.

Минус: `depends_on` между проектами не работает — сервис обязан сам уметь
переподключаться к базе (для FastAPI это штатно: `restart: unless-stopped` +
переподключение пула SQLAlchemy).

### Вариант C. Своя база каждому сервису

У каждого сервиса свой контейнер PostgreSQL. Максимальная изоляция и независимость,
но: N копий памяти/диска, N отдельных бэкапов, N версий. Оправдано, только если
сервисы живут на разных машинах или требуют extensions/настроек, несовместимых
между собой. Для связки сервисов на одном сервере — плохой вариант.

### Матрица выбора

| Ситуация | Решение |
|---|---|
| 2 сервиса, выкат вместе, «показать заказчику» | **A** |
| 2+ сервиса, разная периодичность обновлений, общая база | **B** |
| Сервисы на разных серверах / разная юрисдикция данных | **C** |
| Требуется «одна база, но чтобы не наступали друг другу в таблицы» | **B** + отдельная `DATABASE` или `SCHEMA` на сервис |

## 5. Подводные камни (учесть ДО объединения)

1. **Имена томов зависят от имени папки.** Починить сразу: задать тому явное
   `name:` и объявить его внешним. Иначе переименование папки или переезд в другой
   compose-проект = «база исчезла» (данные останутся в старом томе, но никто о нём
   не вспомнит).
2. **`max_connections`.** По умолчанию в PostgreSQL их 100. У кабинета каждый
   воркер uvicorn держит свой пул: `UVICORN_WORKERS × (DB_POOL_SIZE + DB_MAX_OVERFLOW)`
   = 2 × (10 + 20) = до 60 соединений. Два таких соседа уже упираются в потолок.
   При добавлении сервиса либо режем пулы, либо поднимаем `max_connections`.
3. **Одна мажорная версия на всех.** Образ `postgres:16-alpine`. Переход 16 → 17 —
   это `pg_dump` / `restore`, а не «пересобрали и запустили».
4. **Один владелец схемы.** Миграции (Alembic) приложения к общей базе должны быть
   у одного сервиса-владельца. Если миграции начнут применять два сервиса — база
   разъедется.
5. **Наружу 5432 не открывать никогда.** Общее — значит «внутри общей docker-сети»,
   а не «на весь интернет». Если процесс живёт на хосте — публиковать строго на
   `127.0.0.1:5432`.
6. **Разные сети ≠ разные данные.** Сеть объявляем один раз (`docker network create`),
   иначе каждый проект создаст свою и DNS-имена перестанут пересекаться.
7. **Бэкап становится общим.** Одна база → общий регламент: `pg_dumpall` или
   `pg_dump` по каждой `DATABASE`, и точка восстановления одна на все сервисы.
   Резервную копию тома `pgdata` «на живую» делать нельзя — только дамп.
8. **Конфликт имён в общей сети.** Если в двух проектах сервис назовут `db`,
   разрешение имён станет неоднозначным. Общий сервис называем `pg`, а старое имя
   `db` оставляем как network alias — тогда кабинет продолжит работать без правки
   его `DATABASE_URL`.

## 6. Целевая раскладка (готовые фрагменты)

```
deploy/
├── platform/docker-compose.yml     postgres + caddy, владеет сетью и томом
├── nginx/statcab.vhost.conf        (как сейчас)
└── caddy/Caddyfile                 домены всех сервисов в одном месте
statcab/docker-compose.yml          только backend + web
crm/docker-compose.yml              только backend + web
```

`deploy/platform/docker-compose.yml`:

```yaml
services:
  pg:
    image: postgres:16-alpine
    environment:
      POSTGRES_MULTIPLE_DATABASES: db_statcab,db_crm
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
    restart: unless-stopped
    networks:
      statcab_net:
        aliases: [db]          # ← старый DATABASE_URL кабинета продолжает работать

  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ../caddy/Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
    restart: unless-stopped
    networks: [statcab_net]

networks:
  statcab_net:
    name: statcab_net          # ← существующий заранее: docker network create statcab_net

volumes:
  pgdata:
    name: statcab_pgdata       # ← имя больше НЕ зависит от папки проекта
  caddy_data:
    name: caddy_data
```

`statcab/docker-compose.yml` (фрагмент — сервис `db` из него **удаляется**):

```yaml
services:
  backend:
    environment:
      DATABASE_URL: postgresql+psycopg2://statcab:${POSTGRES_PASSWORD}@db:5432/statcab
    networks: [statcab_net]
    # depends_on: db — убираем, между проектами он не работает

networks:
  statcab_net:
    name: statcab_net
    external: true             # ← сеть чужая, мы к ней только подключаемся
```

Разделение на уровне баз одной командой (в init-скрипте образа или руками):

```sql
CREATE ROLE statcab LOGIN PASSWORD '…';  CREATE DATABASE db_statcab OWNER statcab;
CREATE ROLE crm     LOGIN PASSWORD '…';  CREATE DATABASE db_crm     OWNER crm;
```

## 7. Чек-лист «сделать в первый вечер»

- [ ] Задать томам явные имена (`name:`) и зафиксировать, что `statcab_pgdata` — общий.
- [ ] Проверить, как проект назван на сервере: `docker volume ls` → чьё это
      `…_pgdata` лежит сейчас, и сверить с именем папки.
- [ ] Создать общую сеть: `docker network create statcab_net`.
- [ ] Вынести `db` в `deploy/platform`, оставить alias `db`.
- [ ] Завести отдельную роль и отдельную базу на каждый будущий сервис.
- [ ] Пересчитать `max_connections` под число сервисов × воркеров × размер пула.
- [ ] Общий регламент бэкапов: `pg_dump` по каждой базе, не копия тома.
- [ ] Один TLS-терминатор (Caddy или хостовый nginx) со списком доменов всех сервисов.
