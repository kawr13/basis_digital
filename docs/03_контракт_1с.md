# Контракт: что должна отдавать 1С в кабинет статистики

ТЗ программисту 1С. Кабинет — **только читает**; в базу 1С не пишет и внутрь не заходит.
Формат — «плоские» строки: агрегаты, проценты и сравнения кабинет считает сам.

## 1. Способ передачи (выбрать один)

| Вариант | Что нужно от 1С | Комментарий |
|---|---|---|
| **A. HTTP-сервис (рекомендуем)** | опубликовать HTTP-сервис с 4 GET-методами ниже | клиент в кабинете уже написан, подключение = 3 строки в `.env` |
| B. OData | опубликовать OData-источник с теми же полями | клиент допилим |
| C. Файл по расписанию | XLSX/JSON/XML в общую папку или по FTP | если HTTP между сетями недоступен |
| D. Прямой SQL к базе 1С | — | **отказываемся**: ломается после каждого обновления конфигурации и грузит учётную систему |
| **E. Push (1С сама отправляет)** | POST на `/api/onec/push` с тем же JSON и заголовком `X-OneC-Token` | если HTTP-ход «кабинет → 1С» закрыт файрволом; см. раздел 5 |

Требования к варианту A:
- доступ по **Basic auth** под отдельной учёткой 1С **только для чтения** (права: чтение нужных регистров, без проведения документов);
- кодировка UTF-8, `Content-Type: application/json`;
- время ответа ≤ 10 с (у клиента таймаут 30 с), объём — сотни строк, не миллионы;
- если данных нет — пустой `items: []`, а не ошибка.

## 2. Эндпоинты

Базовый адрес, например: `http://1c-server/StatCabinet`

| Метод | Назначение |
|---|---|
| `GET /warehouses` | справочник складов/терминалов |
| `GET /balance` | остатки грузов на текущий момент |
| `GET /capacity` | занято/ёмкость по складам |
| `GET /dynamics?from=YYYY-MM-DD&to=YYYY-MM-DD` | обработка по дням |

Общая форма ответа:

```json
{ "snapshot_at": "2026-10-12 18:00:00", "items": [ /* плоские строки */ ] }
```

### 2.1 `GET /warehouses`

```json
{ "items": [
  { "code": "WH-01", "name": "Склад №1 (морозильник)",
    "kind": "cold", "capacity": 3200, "unit": "т" }
]}
```
- `code` — **идентификатор склада в 1С**, неизменный: по нему сопоставляются все остальные данные;
- `kind`: `warehouse` | `cold` | `terminal`;
- `capacity` — плановая ёмкость (если в 1С не ведётся — отдать 0, предел задаст админ кабинета);
- `unit`: `т` | `м³` | `TEU` | `мест`.

### 2.2 `GET /balance` — остатки грузов

```json
{ "snapshot_at": "2026-10-12 18:00:00", "items": [
  { "warehouse_code": "WH-01", "cargo_group": "Минтай с/м",
    "qty": 1250, "weight_t": 1840.5, "overdue_weight_t": 210.0, "avg_age_days": 23.4 }
]}
```
- одна строка = склад × группа груза (не по каждой партии — иначе строк станет слишком много);
- `cargo_group` — группировка, которую согласуем (вид груза / номенклатурная группа / договор);
- `qty` — количество в местах/паллетах, `weight_t` — тонны;
- `overdue_weight_t` — вес, у которого срок хранения превысил норматив (норматив согласуем);
- `avg_age_days` — среднее время хранения на складе.

### 2.3 `GET /capacity` — ёмкость складов

```json
{ "snapshot_at": "2026-10-12 18:00:00", "items": [
  { "warehouse_code": "WH-01", "used": 1905.0, "capacity": 3200, "unit": "т" }
]}
```
- `used` — сколько склад занят сейчас (в тех же единицах, что и `capacity`).

### 2.4 `GET /dynamics?from=...&to=...` — динамика обработки

```json
{ "items": [
  { "warehouse_code": "WH-01", "date": "2026-10-11",
    "inbound_t": 120.5, "outbound_t": 98.2, "processed_t": 218.7,
    "docs_count": 34, "avg_dwell_hours": 62.5 }
]}
```
- одна строка = склад × сутки; пустые дни можно не отдавать;
- `inbound_t` / `outbound_t` / `processed_t` — принято / отгружено / обработано, тонны;
- `docs_count` — число документов обработки за день;
- `avg_dwell_hours` — среднее время от поступления до отгрузки.

Кабинет запрашивает последние 30 суток и пересохраняет их при каждой синхронизации,
поэтому **данные за прошлые даты должны быть стабильны** (повторный запрос даёт те же числа).

## 3. Пример стороны 1С (внешняя обработка / HTTP-сервис)

```1c
// Публикация: ВидЖурналаРегистрации -> HTTP-сервис "StatCabinet", метод Balance (GET).
&НаСервере
Функция Balance(Запрос)
    Ответ = Новый Структура("snapshot_at, items", Формат(ТекущаяДата(),"ДФ=yyyy-MM-dd HH:mm:ss"), Новый Массив);

    Запрос = Новый Запрос(
    "ВЫБРАТЬ
    |   Склады.Код КАК warehouse_code,
    |   ГруппыНоменклатуры.Наименование КАК cargo_group,
    |   СУММ(Остатки.Количество) КАК qty,
    |   СУММ(Остатки.Вес)        КАК weight_t,
    |   СУММ(ВЫБОР КОГДА Остатки.СрокХраненияПревышен ТОГДА Остатки.Вес ИНАЧЕ 0 КОНЕЦ) КАК overdue_weight_t,
    |   СРЕДНЕЕ(Остатки.ВозрастДней) КАК avg_age_days
    | ПОМЕСТИТЬ tmp
    |ИЗ РегистрНакопления.ОстаткиГрузов.Остатки(, ) КАК Остатки
    |   ВНУТРЕННЕЕ СОЕДИНЕНИЕ Справочник.Склады КАК Склады ПО Остатки.Склад = Склады.Ссылка
    |   ВНУТРЕННЕЕ СОЕДИНЕНИЕ Справочник.ГруппыНоменклатуры КАК ГруппыНоменклатуры ПО ...
    |СГРУППИРОВАТЬ ПО Склады.Код, ГруппыНоменклатуры.Наименование");

    // tmp -> Ответ.items (Соответствие/Соответствие -> СериализаторJSON)
    Возврат Новый ОбработкаСервисовВзаимодействия.РезультатHTTPСервиса("200", "application/json; charset=utf-8",
        СериализаторJSON.ЗаписатьJSON(Ответ));
Функция
```

Что нужно согласовать в запросах 1С: **таблицы-источники** (регистры/документы),
единицы веса и **норматив просрочки**. Это и есть предмет вопросов В3–В5 в `01_постановка_и_вопросы.md`.

## 4. Проверка подключения (со стороны кабинета)

```bash
# 1. проверить, что 1С отдаёт JSON
curl -u statcab_ro:пароль "http://1c-server/StatCabinet/warehouses"

# 2. переключить кабинет
#    .env: ONE_C_SOURCE=http, ONE_C_BASE_URL=http://1c-server/StatCabinet, ONE_C_LOGIN/PASSWORD
docker compose up -d backend

# 3. дёрнуть загрузку и посмотреть журнал
curl -X POST -H "Authorization: Bearer <token_admin>" http://localhost:8080/api/sync/run
# ответ: {"status":"ok","rows":184,"source":"http","error":null}
```

Ошибки загрузки не роняют кабинет: они пишутся в `sync_runs.error`, а на экране
так и остаётся последний успешный срез с его временем.

Проверка связи (`POST /api/admin/onec/test`) ограничена сверху: каждый из четырёх
GET живёт `ONE_C_PROBE_TIMEOUT_SEC` (по умолчанию 8 с), установка соединения — 3 с,
вся проверка — ~30 с. Загрузка среза так коротко не живёт: ей нужен
`ONE_C_TIMEOUT_SEC`, у 1С есть право думать минуту.

Синхронизация не накладывается: пока витрину пишет один запуск, и ручной пинк,
и плановый job получают 409 «Синхронизация уже выполняется…». Уводить ручной
пинк в фоновую задачу со статусом в журнале сознательно не стали — причина и
формулировка в `TASKS.md`, раздел «Следующие шаги».

## 5. Режим push (если 1С не может отдавать GET)

Когда кабинет не имеет доступа в сеть 1С (разные контуры, файрвол, «1С может
только отправлять»), 1С сама присылает срез:

```
POST http://<cab-host>:8080/api/onec/push
Content-Type: application/json; charset=utf-8
X-OneC-Token: <секретный токен из ONEC_PUSH_TOKEN>
```

Тело — ровно тот же контракт, что отдают GET-методы, только массивы именованные,
а не `items`:

```json
{
  "snapshot_at": "2026-10-12 18:00:00",
  "warehouses": [
    { "code": "WH-01", "name": "Склад №1 (морозильник)",
      "kind": "cold", "capacity": 3200, "unit": "т" }
  ],
  "balance": [
    { "warehouse_code": "WH-01", "cargo_group": "Минтай с/м", "qty": 1250,
      "weight_t": 1840.5, "overdue_weight_t": 210.0, "avg_age_days": 23.4 }
  ],
  "capacity": [
    { "warehouse_code": "WH-01", "used": 1905.0, "capacity": 3200, "unit": "т" }
  ],
  "dynamics": [
    { "warehouse_code": "WH-01", "date": "2026-10-11", "inbound_t": 120.5,
      "outbound_t": 98.2, "processed_t": 218.7, "docs_count": 34, "avg_dwell_hours": 62.5 }
  ]
}
```

Что важно для программиста 1С:

- **`snapshot_at` — ключ среза.** Кабинет идемпотентно перезаписывает строки по паре
  «срез × склад (× группа груза / сутки)»: можно слать один и тот же срез сколько
  угодно раз, дубликатов не будет. Поэтому `snapshot_at` обязан быть стабильным
  для повторной отправки тех же данных (например, время регламентного задания);
- поля `qty`, `weight_t`, `used`, `capacity` — числа; строки без `warehouse_code`
  (а строки динамики без `date`) кабинет отклоняет со `400` и текстом ошибки;
- склад по новому `code` заводится в справочнике автоматически;
- ответ кабинета: `{"status":"ok","run_id":N,"rows":184,
  "counts":{"warehouses":5,"cargo":96,"capacity":5,"dynamics":78}}`.

Ответы на ошибки:

| Код | Когда |
|---|---|
| `503` | токен не настроен в кабинете (`ONEC_PUSH_TOKEN` пуст) — приём срезов выключен |
| `401` | заголовок `X-OneC-Token` отсутствует или не совпал |
| `400` | JSON не разобран (не тот формат, пустой срез, кривые даты) |

Токен задаёт администратор кабинета: `.env` (`ONEC_PUSH_TOKEN`) или UI-настройка
`onec.push_token` (в админке он показывается маской `***`). Каждая загрузка
попадает в журнал `sync_runs` с `source="push"` — её видно в админке и в
`GET /api/admin/sync/runs`.

```1c
// Пример отправки из регламентного задания 1С.
&НаСервере
Функция ОтправитьСрез()
    Запись = Новый ЗаписьJSON;
    Запись.УстановитьСтроку();
    ЗаписатьJSON(Запись, Срез);   // Структура: snapshot_at, warehouses, balance, capacity, dynamics
    Соединение = Новый HTTPСоединение("cab-host", 8080,,,,, Новый ЗащищенноеСоединениеOpenSSL());
    Запрос = Новый HTTPЗапрос("/api/onec/push",
        Новый СоответствиеHTTPЗаголовков({"X-OneC-Token" = "<секрет>",
                                          "Content-Type" = "application/json; charset=utf-8"}));
    Запрос.УстановитьТелоИзСтроки(Запись.Закрыть());
    Возврат Соединение.ОтправитьДляОбработки(Запрос);
Функция
```

Push и pull можно использовать вместе: расписание в кабинете тянет данные само,
а 1С дополнительно толкает срез после закрытия дня.
