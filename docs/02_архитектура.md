# Архитектура кабинета веб-статистики

## 1. Поток данных

```
        ┌───────────────┐   HTTP GET (read-only, Basic auth)
        │      1С       │ ─────────────────────────────────┐
        │ (первичка)    │                                  │  раз в 15 мин / вручную
        └───────────────┘                                  ▼
                                             ┌───────────────────────────┐
                                             │  коннектор onec/*         │
                                             │  mock | http → Snapshot   │
                                             └───────────┬───────────────┘
                                                         ▼
        браузер менеджера                ┌───────────────────────────┐
        React + Vite                     │  витрина PostgreSQL       │
        (nginx, /api прокси)  ◀───────── │  warehouses, fact_* ,     │
                                         │  sync_runs                │
              ▲                          └───────────────────────────┘
              │  JSON, только чтение
        ┌─────┴─────────┐
        │  FastAPI      │  авторизация, роли, срез по складам, агрегаты в SQL
        └───────────────┘
```

Правила границы:
- в 1С **не пишем** и SQL в неё не пускаем — только чтение опубликованного HTTP-сервиса;
- 1С отдаёт **плоские строки** (без наших агрегатов), проценты/итоги/сравнения считает кабинет;
- дашборд читает только витрину: медленный или недоступный 1С-сервис не роняет интерфейс,
  пользователь видит последний срез и его время.

## 2. Модель данных

**Доступ**
- `users` — логин, ФИО, роль (`admin`/`top`/`manager`), `password_hash`, счётчик неудачных
  входов, `locked_until`, `one_c_ref` (связь с учёткой 1С), `ecnp_thumbprint` (задел под ЭЦП).
- `warehouses` — склады/терминалы из 1С (`code` = идентификатор в 1С, ёмкость, единица).
- `user_warehouse_scopes` — какие склады видит менеджер. **Пусто = все склады** (топ-менеджмент).
- `refresh_tokens` — только SHA-256 от токена, `family_id` для отзыва всей цепочки.
- `audit_log` — входы/выходы/блокировки/действия админа.
- `user_preferences(user_id, key, value)` — раскладка дашборда и фильтры отчётов,
  значение — JSON-строка; ключи ограничены белым списком, размер — 20 КБ.

**Витрина (пишет коннектор)**
- `fact_cargo_balance(snapshot_at, warehouse_id, cargo_group, qty, weight_t, overdue_weight_t, avg_age_days)`
- `fact_warehouse_capacity(snapshot_at, warehouse_id, used, capacity, unit)`
- `fact_processing_dynamics(bucket_date, warehouse_id, inbound_t, outbound_t, processed_t, docs_count, avg_dwell_hours)`
- `sync_runs` — чем, когда и сколько загрузили; при ошибке — текст ошибки.

Уникальные ключи (`snapshot_at + warehouse + группа`) делают загрузку **идемпотентной**:
повторный запуск обновляет строки, а не плодит дубли.

## 3. Авторизация и права

| Шаг | Реализация |
|---|---|
| Хранение пароля | `hashlib.scrypt` (n=16384, r=8), формат `scrypt$N$r$salt$hash`, без нативных зависимостей |
| Access-токен | JWT HS256, TTL 30 мин, держится только в памяти браузера (не localStorage → не крадётся XSS) |
| Refresh | случайные 48 байт, httpOnly + SameSite=Lax cookie, TTL 1 сутки, **ротация** на каждый `/refresh` |
| Повторное использование refresh | считаем признаком кражи: отзываем всю `family_id`, журнал `refresh.reuse` |
| Подбор пароля | 5 неудач → блокировка учётки 15 мин; плюс троттлинг 20 попыток/мин на IP |
| Отключили пользователя | `is_active=false` + отзыв всех его refresh-токенов |
| Смена пароля | отзыв всех активных сессий пользователя |
| Права на данные | каждый эндпоинт метрик фильтрует по `allowed_warehouse_ids(user)`; менеджер чужой склад не увидит даже подставив id |

Пороги загрузки склада: `warning ≥ 85 %`, `critical ≥ 95 %` (константы в `services/metrics.py`).

## 4. API

```
POST /api/auth/login | /refresh | /logout | /change-password
GET  /api/auth/me
GET  /api/warehouses
GET  /api/metrics/summary | /cargo-balance | /warehouse-capacity | /processing-dynamics?days=14
GET  /api/admin/users | POST /api/admin/users | PATCH /api/admin/users/{id} | POST /api/admin/reset-password
GET  /api/settings/preferences | GET|PUT|DELETE /api/settings/preferences/{key}
GET  /api/reports/processing | /cargo | /capacity-trend | /warehouses
GET  /api/reports/processing.csv | /cargo.csv | /capacity-trend.csv
POST /api/sync/run                      # админ: немедленная загрузка из 1С
GET  /healthz
```

Параметры отчётов: `from`, `to` (ISO-дата, период ограничен годом) и `warehouses` —
sписок id через запятую; чужой склад даёт **403**, а не строки в выдаче.
CSV: разделитель `;`, десятичный `,`, BOM в начале — файл открывается в русском Excel двойным щелчком.

Все ответы метрик содержат `snapshot_at` / `data_as_of` — пользователь всегда видит,
**на какой момент** цифры, а не «абсолютную истину».

## 5. Развёртывание

- `docker compose`: `db` (PostgreSQL 16) + `backend` (uvicorn, 2 воркера, не root) + `web` (nginx: SPA и прокси `/api`).
- Фронт и API в одном origin → refresh-cookie не режется SameSite, CORS не нужен в проде.
- HTTPS терминируется вашим nginx; для прод-режима включите `ENVIRONMENT=prod` —
  тогда cookie уходит с флагом `Secure`.
- Один процесс-планировщик (APScheduler) в каждом воркере: при 2+ воркерах синхронизация
  может запускаться параллельно — защита `max_instances=1` плюс идемпотентность загрузки.
  Если инстансов станет много, планировщик выносим в отдельный контейнер-воркер.
