# Кабинет веб-статистики · БазисПорт

Сервис для менеджеров и топ-менеджмента: **статистика порта по отчёту диспетчера**
(суда, вагоны, авто, персонал, ричстакеры), **остатки грузов, ёмкость складов, динамика
обработки** — в удобочитаемом виде. Источник цифр — **1С**, кабинет только читает витрину.

Стек: FastAPI + SQLAlchemy + PostgreSQL · React + Vite + Tailwind · Docker Compose.

---

## Быстрый старт (разработка, без Docker)

```bash
# бэкенд
cd backend
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
python -m pytest                                     # 12 тестов на авторизацию и доступ
uvicorn app.main:app --reload --port 8000
```

При первом запуске создаётся SQLite-база и администратор — **пароль печатается в лог**,
смените его сразу. Демо-менеджеры: `petrov` / `sidorova` / `ivanova`, пароль `demo1234`
(только в dev, в prod их не будет).

```bash
# фронт (в другом терминале)
cd frontend
npm install
npm run dev                                          # http://localhost:5173, API проксируется на :8000
```

**Почему разделы грузятся отдельно.** Страницы подключены лениво (`React.lazy` в
`src/App.tsx`): экран входа не тянет «Статистику», админку, постановку судов и отчёты,
а после выката браузер берёт из кэша неизменный `react-vendor` и чанки тех разделов,
которые человек не открывал. Поэтому `npm run build` печатает несколько строк
`dist/assets/*.js`: `index-*.js` — каркас и маршруты (это и есть старт входа),
`react-vendor-*.js` — react/react-dom/react-router, остальное — по чанку на раздел;
`gzip:` — сколько реально едет по сети. `chunkSizeWarningLimit` не поднят: разрастётся
страница — сборка скажет сама. Если чанк раздела не приехал (старый `index.html` после
выката), кабинет один раз перезагружает документ сам; если и не помогло — показывает
«Раздел не загрузился» с кнопкой, а не белый экран.

## Прод (Docker Compose)

```bash
cp .env.example .env        # заполнить POSTGRES_PASSWORD и SECRET_KEY
docker compose up -d --build
docker compose logs backend | grep администратор
```

Кабинет — на `http://localhost:8080`. Дальше ставится за ваш nginx/HTTPS
(см. `frontend/nginx.conf` как образец: `/api` проксируется в бэкенд, фронт — SPA).

### Выкат на сервер: релизный архив

С рабочей машины (Windows) собирается чистый архив без мусора (`.git`,
`node_modules`, `.venv`, локальные БД, `.env`):

```powershell
cd D:\basis\statcab
powershell -ExecutionPolicy Bypass -File .\pack_release.ps1
# → release\statcab-<дата-время>.zip (проверенные пути для linux unzip)
```

На сервере:

```bash
scp release/statcab-*.zip user@server:/tmp/
# на сервере:
mkdir -p /opt/statcab && tar -xf /tmp/statcab-*.zip -C /opt/statcab --strip-components=1
cd /opt/statcab
cp .env.example .env
openssl rand -hex 32   # SECRET_KEY
openssl rand -hex 16   # POSTGRES_PASSWORD
# заполнить .env: POSTGRES_PASSWORD, SECRET_KEY, ADMIN_PASSWORD;
# доступ без HTTPS → COOKIE_SECURE=false
docker compose up -d --build
docker compose logs backend | grep администратор   # пароль первого админа
```

Образ собирается на сервере (локальный Docker для этого не нужен).
Расчёт ресурсов, обновление, откат и бэкап — `docs/06_деплой_на_сервер.md`.

## Админка: пользователи, склады, 1С, настройки

Всё под ролью `admin` (кроме `/api/settings/public` — он для любой авторизованной
роли, и `/api/onec/push` — там токен 1С, а не JWT).

| Метод | Что делает | Коды |
|---|---|---|
| `GET /api/admin/settings` | значения + `defaults` + `overridden` (что перебито из `.env`) | 200, 401, 403 |
| `PUT /api/admin/settings` | частичный патч; после сохранения перепланирует синхронизацию | 200, 422 (русский текст), 403 |
| `POST /api/admin/settings/reset` | вернуть ключи к значениям из `.env`/DEFAULTS | 200, 422, 403 |
| `GET /api/settings/public` | безопасный набор (периоды, пороги) для любой роли | 200, 401 |
| `POST /api/admin/onec/test` | проверка связи: 4 GET по очереди, ошибки — в `checks[].error` | 200, 403 |
| `POST /api/admin/sync/run` | загрузить витрину из 1С сейчас | 200, 403 |
| `GET /api/admin/sync/runs?limit=20` | журнал загрузок (pull и push), свежие сверху | 200, 403 |
| `GET/POST /api/admin/warehouses`, `PATCH/DELETE /api/admin/warehouses/{id}` | справочник складов; PATCH выключает, DELETE удаляет (со статистикой — только `?purge=true`) | 200/201, 204, 400, 404, 409, 403 |
| `POST /api/admin/users/{id}/unlock` | снять блокировку после неверных попыток | 200, 404, 403 |
| `DELETE /api/admin/users/{id}` | удалить учётку целиком (выключить — PATCH `is_active`); журнал и постановки остаются без автора | 204, 400 (себя), 404, 403 |
| `GET /api/admin/audit?limit=100` | последние записи журнала действий | 200, 403 |
| `POST /api/onec/push` | 1С сама присылает срез (`X-OneC-Token`) | 200, 400, 401, 503 |
| `GET /api/dispatcher/overview?from&to&shift` | агрегаты «Статистики»: KPI, сутки, причалы, суда, персонал, ж/д и авто, подход судов и вагонов | 200, 400, 401 |
| `GET /api/dispatcher/meta` · `GET /api/dispatcher/day?date` | границы витрины и смены / одна смена построчно | 200, 401, 404 |
| `POST /api/admin/dispatcher/import` | разобрать «Отчёт диспетчера» (путь `{"path": "..."}` или `{"filename", "content_base64"}`) и положить в витрину | 200, 400, 403 |
| `GET /api/dispatcher/rows?from&to&shift&kind&key` | строки витрины для дриллдауна: разрез в `kind` (`vessel`, `berth`, `cargo`, `rail_cargo`, `truck_cargo`, `station`, `rail_move`, `platform`), `key` необязателен; ответ сам описывает колонки и итоги | 200, 400, 401 |
| `GET /api/admin/dispatcher/status` | путь к файлу, есть ли он, автозагрузка, что и когда лежит в витрине | 200, 403 |

Настройки времени выполнения (`app_settings`, JSON в TEXT): приоритет **БД →
`.env` → DEFAULTS**, поэтому существующий `.env` продолжает работать, пока админ
ничего не поменял в UI. Ключи: `onec.source|base_url|login|password|push_token|timeout_sec`,
`sync.enabled|interval_minutes|window_days`, `ui.dynamics_days`,
`reports.default_days`, `thresholds.capacity_warn|capacity_crit`,
`security.max_failed_logins|lockout_minutes`, `dispatcher.source_path`,
`dispatcher.auto_import`, `dispatcher.default_period_days`,
`dispatcher.max_period_days`; вид страницы —
`statistics_mode`, `statistics_layout`, `statistics_layout_lite`,
`ui.hidden_sections` (какие разделы кабинета не показывать всем). Секреты (`onec.password`,
`onec.push_token`) наружу не отдаются: в ответе маска `***` и флаг `..._set`.
Любая запись настроек оставляет след в `audit_log` (`admin.settings_update`).

Расписание живёт в `app.state.scheduler`: `PUT /api/admin/settings` вызывает
`scheduling.reschedule()` — меняет интервал, снимает job при `sync.enabled=false`
или заводит его, не перезапуская сервис.

## Переключение на настоящую 1С

1. Программист 1С публикует HTTP-сервис по контракту `docs/03_контракт_1с.md`
   (4 GET-эндпоинта, учётка только для чтения).
2. В `.env`: `ONE_C_SOURCE=http`, `ONE_C_BASE_URL=http://<1c-server>/StatCabinet`,
   логин/пароль отдельной учётки 1С.
3. `docker compose up -d` → `curl -X POST localhost:8080/api/sync/run` (под админом).

Пока 1С нет — `ONE_C_SOURCE=mock`, цифры демонстрационные, но структура и экраны настоящие.

## Почти реальное время

Сокета нет и не планируется: данные приходят из 1С раз в N минут, а вот замечать их
быстро кабинет обязан.

| кто | что делает |
|---|---|
| бэкенд | `GET /api/meta/freshness` — метка среза, последний успешный синк, признак устаревания |
| фронт | раз в 15 с опрашивает свежесть; изменилась метка → сам перезапрашивает метрики |
| фронт | когда вкладка скрыта — не стучится; при возврате обновляется сразу |
| админ | `ui.refresh_seconds` (5…900, по умолчанию 60) — период полной авто-перезагрузки дашборда |

«Устаревшими» данные считаются, если успешного обмена с 1С не было дольше **2.5 интервалов**
синхронизации (`STALE_FACTOR` в `app/api/meta.py`) — чтобы не шуметь из-за одного пропущенного тика.

## Постановка судов

Отдельный от 1С участок кабинета: план постановки судов к причалам, который ведёт человек.

* сетка читается как лист миллиметровки: слева направо — время (сутки разбиты на 4 слота
  по 6 часов), сверху вниз — длина причала, 10 метров на ячейку (100 м = 10 ячеек, ячейка
  сжата до 12 px, чтобы на экран помещалось больше причалов).
  У причала свой блок с линейкой отметок, полоса судна стоит ровно на своих метрах;
* у судна задают длину (м) и отметку швартовки (м от начала причала) — это и есть
  параметр, по которому кабинет считает, влезло ли судно;
* создать/поправить можно на любой период, посмотреть — тоже на любой: судно, начатое
  в прошлом месяце, попадёт в майский план и дорисуется пунктирным краем;
* чтобы не вбивать одно и то же судно заново (ставки ходят циклами), в окне
  «Новая постановка» есть «Скопировать из предыдущей постановки…»: список прошлых
  постановок за 4 месяца, по строке на судно (последняя стоянка), с поиском по
  названию. Причал, груз, тоннаж, длина, отметка и цвет кочуют в форму, а даты —
  новые: длительность стоянки сохраняется, начало ставится на сегодня;
* два судна у одного причала не поставят друг на друга: конфликт только если они
  пересекаются и по времени, и по метрам — кабинет скажет, какое судно мешает и где
  именно пересекаются метры («пересечение по длине 30–60 м»);
* судно длиннее причала или вылезшее за его край не принимается (причал 100 м, судно
  140 м — «не встанет»); в форме есть кнопка «Найти свободное» — бэкенд подскажет
  отметку, где места хватает;
* «✏ Корректировка» включает перетаскивание: полосу тянут мышью — горизонталь это слоты
  (шаг 6 часов), вертикаль — место у причала (шаг 5 м); отпустили — сохранилось. Судно
  можно перевести и на другой причал — его тянут вниз или вверх до нужного причала,
  отметку швартовки считают по новому причалу. Стрелки двигают полосу под фокусом.
  Создавать судно по-прежнему нужно окном постановки — там видно, куда оно встанет,
  до появления строки;
* строка «Ожидание» в конце плана — карман для судов вне причалов (ждут черёды, груза,
  перешвартовки): в нём можно стоять скольким угодно судам одновременно, метраж и конфликты
  к нему не применяются; перетаскивание судна из «Ожидания» к причалу создаёт **копию со
  стрелкой**, оригинал остаётся в кармане, пока судно физически не придёт;
* правая кнопка по судну (в режиме «✏ Корректировка») — «Временное перемещение»:
  полупрозрачная копия прицепляется к курсору, отпускание в ячейку ставит её на причал,
  слоты и метры, и от оригинала к копии сама рисуется стрелка перешвартовки (пунктирная
  рамка и полупрозрачность копии — признак черновика; оригинал удалили — стрелка погасла);
* поле плана тянется от левой границы до правой: ширина слота считается от ширины
  экрана, поэтому неделя и две недели не оставляют справа пустой полосы;
* «⤓ PDF» скачивает файл, который собрал бэкенд: в лист попадает **только видимая
  область** — те сутки и причалы, что сейчас в окне сетки, крупно, а не весь период,
  сжатый до нечитаемого. Лист — A4 альбом, текст настоящий (кириллица, поиск,
  копирование), судно за границей кадра обрезано пунктиром. Следующий кусок так же:
  прокрутил план → «⤓ PDF»; имя файла строится по окну, а не по периоду, — два листа
  одного месяца не путаются;
* справочник причалов (код, осадка, метраж, порядок) ведётся в админке — вкладка
  «Администрирование → Причалы»: добавить, поправить длину, снять причал с линии
  (исчезнет из плана, постановки останутся), удалить пустой. При первом запуске
  справочник заполняется типовыми РП-1…РП-6;
* права настраиваются в админке (вкладка «Настройки»): `vessels.view_roles` — кто видит план,
  `vessels.edit_roles` — кто ставит и правит суда, `vessels.delete_roles` — кто удаляет. Роли
  через запятую (`admin, top, manager`): диспетчеру выдают право ставить суда, не повышая роль;
  закрытый просмотр убирает и вкладку, и маршрут;
* если нужен один человек, а не роль целиком — право ставят в его карточке
  (Администрирование → Пользователи → «Постановка судов»: нет / смотреть / править / полный).
  Оно перекрывает роль в обе стороны, работает как доступ к складам — точечно по человеку;

Подробнее и со списком открытых вопросов — `docs/04_постановка_судов.md`.

## Индикаторы порта (отчёт диспетчера)

Главная страница кабинета. В отличие от складов 1С это **порт целиком**: причалы,
суда, вагоны, автомашины, персонал бригады и ричстакеры. Поэтому цифры здесь не
фильтруются по складам — доступ к ним имеет любой авторизованный.

Две смены в сутках: `08–20` (день) и `20–08` (ночь). Пока 1С не отдаёт срез по
HTTP, витрину наполняет файл `Отчет диспетчера.xlsm` — один лист на смену.

| что на экране | зачем |
|---|---|
| 9 плиток KPI | грузопоток, план, судозаходы, темп т/ч, потери времени, вагоны, авто, явка, ричстакеры |
| грузопоток по суткам (столбики факт + план, линия потерь, линия судозаходов) | клик по суткам открывает панель смены: день и ночь построчно |
| нарастающий итог, парето грузов, план/факт по суткам | равномерность и «кто даёт тоннаж» |
| круги грузопотока и «импорт/экспорт» | структура груза |
| причалы, топ судов, пузырьки «темп × машинное время» | где стоят потери и кто тормозит |
| радар «день против ночи», тепловая карта «день недели × неделя» | сравнение смен и будни/выходные |
| персонал, выбытия, ричстакеры | укомплектованность и исправность техники |
| вагоны и авто по суткам + номенклатура | сухопутный контур |
| выводка и постановка вагонов (план/факт, задержка против плана, типы вагонов) | сухопутный контур со стороны пути |
| платформы, выведенные из аренды (остаток, на терминале, отправлено) | чей парк и где он сейчас |
| «суда на подходе», «ж/д на подходе» | план на ближайшие сутки |

Все блоки — свои SVG (без библиотек), живут в `WidgetGrid`, поэтому их можно
переставлять, тянуть за края и скрывать; раскладка сохраняется на сервере.

**Два режима.** «Подробно» — 34 блока, включая кольца структуры, радар смен,
пузырьки судов, тепловую карту дней недели и четыре спидометра. «Консервативно»
— 30 блоков в одном визуальном языке: те же цифры, но полосы, столбцы, линии и
таблицы вместо колец, радаров, пузырьков, тепловых карт и спидометров. Режим и
порядок блоков хранятся на сервере отдельно для каждого режима
(`statistics_mode`, `statistics_layout`, `statistics_layout_lite`).

**Клик ведёт в таблицу.** Полоса причала → строки обработки причала, столбец
сутков → смена построчно, тип вагона → составы выводки и постановки, владелец
платформ → баланс по суткам. Такому дриллдауну не нужны свои запросы: бэк
`GET /api/dispatcher/rows` отдаёт и строки, и описание колонок, и итоги —
фронт рисует таблицу и CSV, не зная состава разреза.

**Как попасть данным в витрину**: Администрирование → «1С и синхронизация» →
«Отчёт диспетчера»: путь к файлу на сервере + «Импортировать по пути», либо
«Загрузить файл…» прямо из браузера. Повторный импорт **заменяет** смены из
файла, поэтому дубликатов не будет. Настройки: `dispatcher.source_path`,
`dispatcher.auto_import` (забрать файл при старте, если он свежее последней
загрузки), `dispatcher.default_period_days` (сколько суток считать по умолчанию)
и `dispatcher.max_period_days` (самый длинный период, который кабинет
согласится посчитать) — см. `docs/05_статистика_порта.md`.

Разбор файла изолирован от остального кабинета: `onec/dispatcher_xlsm.py`
(листки → dataclass-ы) → `onec/dispatcher.py::apply_snapshot` (запись) →
`services/dispatcher.py` (агрегаты). Когда 1С начнёт отдавать тот же срез по
HTTP, менять придётся только разбор — экраны и агрегаты останутся. Контракт
будущего HTTP-среза и разбор текущего листа — `docs/05_статистика_порта.md`.

## Палитра и стиль

Цвета взяты не «на глаз», а сняты с рабочего `cab.basisport.ru` (computed styles + `css/main.css`):
шапка `.navbar-mrp` — `#1b3360`, ховер в шапке — `#2fbaec`, заголовки панелей bootstrap — `#337ab7`,
активные пункты — `#428bca`, фокус полей — `#66afe9`. Всё это лежит в `tailwind.config.js`
в объекте `brand`.

**Логотип.** Фирменный знак лежит в `frontend/public/` в двух вариантах: `logo.svg`
(оригинал, тёмно-синие пути `#063058` + голубые `#26AAE1` — для светлых фонов) и
`logo-light.svg` (тёмно-синие пути перекрашены в белый — для navy-шапки и синей панели
входа). Ставить оригинал на тёмный фон нельзя: `#063058` на `#1b3360` не читается вообще.

Стиль — строгий светлый: синяя шапка (`brand.navy`, белый текст, голубая hairline снизу),
светлый фон страницы, белые плашки с МЯГКОЙ РАССЕЯННОЙ тенью (`shadow-panel` — три слоя
полупрозрачного сине-серого `rgba(16,24,40,.05/.10/.14)`, без чёрных краёв).

Шкала `ink` в светлой теме «перевёрнута»: `ink-100` — самый тёмный (основной текст),
`ink-900` — самый светлый (поверхность плашки). Имена классов при этом не менялись,
поэтому `text-ink-300` / `border-ink-700` работают везде без правок в компонентах.

Контраст подобран под WCAG AA (считался скриптом): второстепенный текст `ink-300` — 6.8:1,
подписи и шапки таблиц `ink-400` — 5.0:1, белый на navy — 12.4:1, `accent #1668a8` — 5.9:1,
сигнальные `ok/warn/crit` и янтарь затемнены под белый фон (5.3–6.2:1). Столбцы графика
синие (`#337ab7`, 4.6:1): янтарные на белом давали бы 2.2:1.

> Пропажа «стекла»: `backdrop-filter` и полупрозрачность из прошлой итерации убраны —
> на белом фоне они выглядели грязью. Если захотим вернуть стекло, оно имеет смысл
> только на тёмных поверхностях (шапка, модальные окна).

## База данных и ORM

- **СУБД**: PostgreSQL 16 в проде (`docker-compose.yml`), SQLite в разработке — один и тот же код,
  переключение одной переменной `DATABASE_URL`.
- **ORM**: SQLAlchemy 2.0 (декларативные модели, `backend/app/models.py`), 22 таблицы (9 витрины «Отчёта диспетчера»).
  Обработчики FastAPI синхронные — пул соединений SQLAlchemy, без asyncio-драйверов.
- **Миграции**: сейчас `create_all` при старте; при появлении боевых данных — Alembic
  (`alembic init` + первая ревизия), это отдельная задача в плане.
