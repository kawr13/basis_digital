## 1. Сжатие ответов API

**Факт.** `GET /api/dispatcher/overview?from=2026-09-14&to=2026-10-13` с
`Accept-Encoding: gzip, deflate, br` отвечает `content-length: 70065` и **без**
`content-encoding`. Статика при этом сжимается.

**Причина.** В `frontend/nginx.conf` есть `gzip on` и `gzip_types application/json`,
но нет `gzip_proxied any`. По умолчанию nginx проксируемые ответы не сжимает, а весь
API — это `proxy_pass`.

**Сделать.**
- `frontend/nginx.conf`: `gzip_proxied any;` `gzip_comp_level 6;` `gzip_min_length 1024;`
  `gzip_vary on;` (не трогать `gzip_types` — там уже есть `application/json`).
- `deploy/nginx/statcab.vhost.conf`: то же, чтобы работало и когда кабинет проксируют
  одним nginx без внутреннего.
- `docs/06_деплой_на_сервер.md`: короткая заметка, почему без `gzip_proxied` gzip не работает.

**Проверка.** Новый тест `backend/tests/test_web_config.py` читает оба конфига и требует
наличия директив. Живьём: `curl -sD - -H 'Accept-Encoding: gzip' .../api/meta/freshness`
→ `content-encoding: gzip`.

## 2. Кэш `index.html`

**Факт.** В `frontend/nginx.conf` заголовки отдачи стоят только в regex-локейшене
`\.(js|css|svg|woff2?)$`. Для `index.html` `Cache-Control` не выставлен вообще —
браузер кеширует эвристически по `Last-Modified`. После релиста пользователь остаётся со
старым `index.html`, который ссылается на уже удалённые хэшированные JS: белая страница
до Ctrl+F5.

**Сделать.** `location = /index.html { add_header Cache-Control "no-store"; ... }`;
для статики оставить `public, immutable, max-age=31536000`. Проверить, что
`try_files ... /index.html` для SPA-маршрутов тоже отдаёт `no-store`.

**Проверка.** Тот же `test_web_config.py`.

## 3. Размер тела запроса

**Факт.** `client_max_body_size 2m` и в `frontend/nginx.conf`, и в
`deploy/nginx/statcab.vhost.conf`. Импорт «Отчёта диспетчера» идёт base64 (+33 %),
поэтому файл тяжелее ~1.4 МБ не грузится — nginx отвечает 413 до всякого кода приложения.

**Сделать.** Поднять до `16m` в обоих местах, добавить `proxy_request_buffering off;`
в `location /api/` внутреннего nginx (файл уходит в бэкенд потоком). В
`DispatcherImport.tsx` показывать понятную ошибку на 413.

**Проверка.** `test_web_config.py` требует `client_max_body_size 16m` в обоих конфигах.

## 4. Кэш агрегатов витрины

**Факт.** `services/dispatcher.py:overview()` на каждый запрос грузит 9 таблиц витрины
за период **и** за предыдущий период (`load_rows()` дважды) и считает всё в Python:
31 день — 110 мс, 365 дней — 1207 мс и 743 КБ JSON. Данные при этом меняются раз в
15 минут (синк 1С) или в момент импорта `.xlsm`.

**Сделать.**
- Кэш собранного `dict` в памяти процесса: ключ `(date_from, date_to, shift)`,
  версионирование по `max(updated_at)` фактовых таблиц (счётчик уже есть в
  `services/dispatcher.py`), вытеснение по LRU, максимум ~8 записей, обязательно под
  `threading.Lock` (воркеров несколько).
- Инвалидация — по версии данных, ручного сброса не нужно; импорт `.xlsm` обязан
  сдвигать версию (посмотреть, что `apply_snapshot` обновляет `updated_at`).
- HTTP: `ETag` + `Cache-Control: private, no-cache` на
  `/api/dispatcher/overview|rows|meta`, обработка `If-None-Match` → 304.
  Именно `no-cache`, а не `max-age=60`: импорт `.xlsm` обязан быть виден сразу,
  а удорожания всё равно нет — неизменившийся ответ приходит как 304 без тела.
  На `/api/meta/freshness` кэш не вешать.

**Проверка.** pytest: повторный вызов `overview` не обращается к БД (посчитать запросы
через `sqlalchemy.event`), после записи новой смены кэш протухает, `If-None-Match`
возвращает 304. Все существующие тесты зелёные.

**Итог (замер 2026-10-25 после правки, тот же разрез в 34 310 строк).**
31 сутки: 110 мс → 5.8 мс; 365 суток: 1129 мс → 7.3 мс, тело ответа при неизменных
dанных — 0 байт вместо 743 КБ. Новое: `backend/app/services/data_cache.py`,
`backend/tests/test_dispatcher_cache.py` (11 тестов).

  ответа показывается, а не проглатывается.
- `docs/05_статистика_порта.md`: зафиксировать лимит.

**Проверка.** pytest: 400 на `from=2025-10-14&to=2026-10-13`, 200 на 183 сутках,
настройка перебивается из админки. `tools/ui_statistics.mjs` зелёный.

## 6. Лимит строк дриллдауна + серверный CSV

Выгрузку CSV клиент делает из уже загруженных строк
(`DispatcherRowsPanel.tsx`), поэтому простое усечение срежет часть выгрузки.

**Сделать.**

  десятичная запятая, BOM — как в `services/reports.py`.
- Фронт: кнопка CSV ведёт на серверный адрес (с access-токеном в заголовке — взять
  существующий `requestBlob`), при `truncated` показывает «показаны первые N из M».

**Проверка.** pytest: `limit` работает, `total` честный, CSV совпадает по строкам с
`rows` без лимита. `tools/ui_statistics.mjs` обновлён и зелёный.

## 10. Обращения к 1С не занимают воркер

**Факт.** `POST /api/admin/onec/test` делает четыре последовательных GET с
`ONE_C_TIMEOUT_SEC=30` — до 120 секунд занятого потока; `POST /api/admin/sync/run` —
так же. Один клик «проверить связь» при недоступной 1С подвешивает кабинет. Плюс
`http_source.py:_client()` создаёт `httpx.Client` на каждый вызов — без keep-alive.

**Сделать.**
- Отдельный таймаут проверки связи: `one_c_probe_timeout_sec` (по умолчанию 8),
  `connect` — 3 с. Проба суммарно не дольше ~30 с.
- Общий `httpx.Client` на источник (создать один раз, закрыть при остановке приложения).
- Синхронизацию защитить `threading.Lock`: повторный запуск, когда уже идёт, — 409
  с русским текстом вместо второй параллельной выгрузки.
- Увод ручного пинка в фон (фоновая задача + журнал `sync/runs`) — **не** в этом пункте,
  записать в «следующие шаги» этого файла.

**Проверка.** pytest: таймаут пробы ограничен (мок, отвечающий с задержкой), повторный
`sync/run` во время активного — 409. Тесты на 1С не стали медленнее.
